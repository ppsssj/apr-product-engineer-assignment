# Architecture Decisions

This document records architecture choices for the APR Product Engineer assignment.

`ASSIGNMENT.md` remains the canonical source of truth. Architecture exists to explain **how and why** the requirements are implemented; it must never weaken or reinterpret them.

## Evidence Policy

Every high-impact decision must separate facts from judgment.

Evidence types:

- **Assignment evidence** — explicit requirement from `ASSIGNMENT.md`.
- **Starter evidence** — behavior/configuration verified in the provided starter repository.
- **Official documentation** — first-party framework/database/browser documentation.
- **Engineering judgment** — our conclusion from the evidence, with alternatives and trade-offs stated explicitly.

Decision status:

- `DECIDED` — enough evidence exists to implement this choice.
- `PROVISIONAL` — current preferred choice, but repository/design inspection can still change it.
- `OPEN` — do not implement the affected area until the decision is resolved.

Do not cite blog posts or AI-generated claims when an official source is available.

Verification follows the runtime boundary rather than treating one test type
as sufficient for every risk:

```text
JUnit/Mockito + Vitest
  → PostgreSQL Testcontainers integration
  → production Docker Compose smoke
  → selected Chromium Playwright regression
```

- Backend unit/service tests cover controller contracts, validation,
  requester resolution, cursor codecs and transaction decisions without
  requiring a database.
- Six Testcontainers suites run 31 tests against PostgreSQL 16 with the real
  Flyway migration and `SeedInitializer`; they cover schema constraints,
  repository SQL, keyset/search behavior, persistence and concurrent locking.

  backend and frontend jobs pass, then verifies health, API, SSR, seed history
  and the baked browser API base.
- Three committed Playwright flows run in Chromium at 375×778 against that
  stack. They protect search/likes/mobile invariants, comment More/revisit
  behavior and delete-dialog keyboard focus. They do not replace the broader
  manual/runtime evidence.

# Architecture Review Finalization — 2026-09-29

**Review status:** `COMPLETE`
**Authoritative record:** This section supersedes the prior proposed ADR text and status labels when they conflict. It finalizes the implementation direction only; it does not add dependencies, schema, or product code.

## Shared Constraints and Invariants

- **Assignment evidence:** Java 17/Spring Boot 3.x, Next.js 15 App Router, PostgreSQL, full-stack `docker compose up`, soft deletion, requester-specific likes, bounded pagination, seed-ID preservation, and the immutable `/dev-user`/`GET /health` contracts are mandatory.
- **Repository evidence:** JDBC and PostgreSQL are already declared; JPA, migration tooling, state/data libraries, and UI libraries are absent. The seed has 42 posts, 2,076 comments, explicit IDs, aggregate `likeCount`, and no historical user-like data or `commentCount`.
- **Scope invariant:** no user table, invented historical like users, deletion timestamps fabricated from seed data, speculative distributed architecture, or unnecessary abstraction layer.

## Final Decisions

| Decision | Status | Decision and fit | Alternatives considered / accepted trade-off | Implementation verification |
| --- | --- | --- | --- | --- |
| Persistence | `DECIDED` | Use Spring JDBC `JdbcClient` with explicit SQL repositories. It is compatible with the declared JDBC starter and keeps soft-delete, ownership, aggregate count, like, and pagination queries visible. | Add JPA/Spring Data JPA; rejected because it adds an undeclared ORM dependency and does not remove the assignment’s query-specific work. | Compile and integration-test CRUD, soft-delete filters, ownership, and row mapping. |
| Schema migration | `DECIDED` | Add Flyway for versioned schema migration only; load the provided JSON in application code rather than duplicate it as migration data. The persistent DB volume needs schema-history semantics across restarts. | `schema.sql`; simpler and dependency-free, but less explicit for schema evolution. Flyway costs an added dependency and PostgreSQL module. | Clean-volume and restart tests show migrations apply once and schema history is stable. |
| Seed lifecycle | `DECIDED` | Run idempotent JSON import through an `ApplicationRunner` after Flyway. Insert explicit IDs, preserve later user mutations, and record completed import only after the transaction succeeds. | Reset/update rows at every startup; rejected because it overwrites user-created or edited state. | Startup/restart test: no duplicate records, deleted IDs stay deleted, and sequences allow a new row. |
| IDs | `DECIDED` | Use `BIGINT GENERATED BY DEFAULT AS IDENTITY`; import explicit seed IDs, then align each sequence above its seeded maximum. | Application-side ID allocation; rejected as extra state without assignment value. | Seed IDs remain exact; first created post/comment receives a non-conflicting ID. |
| Soft delete | `DECIDED` | Use `is_deleted BOOLEAN NOT NULL DEFAULT FALSE` for posts and comments. The seed supplies deletion membership, not a deletion instant, so a boolean represents known facts without inventing timestamps. | `deleted_at`; rejected because it fabricates a seed timestamp. | Deleted rows remain stored but are excluded from list/detail/count/mutation reads. |
| Likes | `DECIDED` | Store `posts.base_like_count` plus `post_likes(post_id, user_id)` with a unique key. Calculate `likeCount` from both and `isLiked` from the requester row. | Mutable aggregate counter only, or invented historical like users; rejected because both lose/alter seed facts. | Toggle twice as one requester and fetch as another; count and `isLiked` remain correct. |

This fits newest-first infinite scrolling under concurrent creates/deletes. | Offset pagination; simpler but can drift while scrolling. It also still needs a separate total count. | Bounded page requests are deterministic and adjacent pages have no duplicates/skips. |

| Client/server boundary | `DECIDED` | Keep App Router route shells server by default; isolate interactive, cookie-dependent community features behind client boundaries and send browser API requests with `credentials: "include"`. | Mark every component client-side; rejected because it broadens the client bundle and loses the App Router default boundary. | `/dev-user` cookie drives requester-sensitive browser calls without changing the immutable page. |
| Styling | `DECIDED` | Use existing `globals.css` for Pretendard/reset/tokens and CSS Modules for component/page styles. No UI framework is needed for this mobile take-home. | Tailwind or a UI kit; rejected because neither is installed and both add configuration/dependency surface. | Next build and 375px visual review once the design asset is supplied. |

## External Evidence

- **Spring Framework 6.2 — [JdbcClient](https://docs.spring.io/spring-framework/reference/data-access/jdbc/core.html):** `JdbcClient` has been available since Spring Framework 6.1 as a fluent unified JDBC query/update API. This supports the declared Spring Boot 3.5 JDBC path.
- **Spring Boot 3.5 — [Database Initialization](https://docs.spring.io/spring-boot/3.5/how-to/data-initialization.html):** recommends one schema-initialization mechanism; Flyway runs on startup and PostgreSQL requires its database-specific Flyway module.
- **Spring Boot 3.5 — [SpringApplication](https://docs.spring.io/spring-boot/3.5/reference/features/spring-application.html):** `ApplicationRunner` runs just before `SpringApplication.run` completes, which supports one-time startup bootstrap work.
- **PostgreSQL 16 — [Identity Columns](https://www.postgresql.org/docs/16/ddl-identity-columns.html):** `GENERATED BY DEFAULT` identity columns permit explicitly supplied values while generating values when omitted.
- **PostgreSQL — [LIMIT and OFFSET](https://www.postgresql.org/docs/current/queries-limit.html):** page subsets need deterministic ordering and skipped offset rows are still computed; this supports the keyset trade-off.
- **TanStack Query v5 — [Infinite Queries](https://tanstack.com/query/latest/docs/framework/react/guides/migrating-to-v5):** infinite queries model paginated page data and v5 provides bounded retained pages through `maxPages`.
- **Next.js — [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components):** pages/layouts are Server Components by default; Client Components are appropriate for browser APIs, events, effects, and state.
- **MDN — [Intersection Observer API](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API):** provides asynchronous intersection observation and explicitly lists infinite scroll as a use case.
- **MDN — [Intl.RelativeTimeFormat](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/RelativeTimeFormat):** documents the native locale-sensitive relative-time formatter.

# P2A Read API Implementation Update — 2026-09-29

- Requester resolution is implemented by one `RequesterResolver` with deterministic precedence `x-user-id` header > `x-user-id` cookie > `apr_tester`. Blank or whitespace-only values are absent, and no user table is introduced.
- Both read collections accept optional `limit` and `cursor`. The default limit is 20, the accepted range is 1–50, and invalid limits or cursors return HTTP 400 JSON errors.
- The canonical order is `(created_at DESC, id DESC)`. The next-page predicate compares the same timestamp and ID pair, and repositories fetch `limit + 1` rows to decide whether `nextCursor` exists without using `OFFSET`.
- The opaque cursor payload is the exact `Instant` text plus the numeric ID, separated by `|`, encoded as URL-safe Base64 without padding. Decoding rejects non-canonical Base64, invalid timestamps, non-positive/invalid IDs, and malformed payload structure.
- `GET /api/posts`, `GET /api/posts/{postId}`, and `GET /api/posts/{postId}/comments` are the only P2A endpoints. Post page rows derive `likeCount`, requester-specific `isLiked`, and readable `commentCount` in one bounded SQL query; a separate count query supplies full `total`.
- Missing and soft-deleted posts both return the same 404 JSON contract. Comment reads first require a readable parent post. At the P2A cutoff, mutation validation and ownership enforcement were intentionally deferred to P2B.

# P2B Mutation API Implementation Update — 2026-09-29

- The six required mutation routes use focused request/response records and keep the P2A read contract unchanged. Post create/update share one explicit validator; title length is measured with `String.codePointCount`, blank checks do not trim the stored value, and comment content has no invented maximum length.
- Rejecting blank comment content is a `PRODUCT_DECISION`: the assignment requires comment creation but gives no explicit blank rule. A nonblank requirement prevents empty persisted comments without introducing a length cap.
- `PostMutationService` and `CommentMutationService` are the authoritative ownership and transaction boundaries. Repositories expose SQL primitives and do not encode HTTP status semantics.
- Every mutation method is service-level `@Transactional`. Readable target rows are locked before ownership checks or multi-step changes; like toggle serializes on the readable post row and relies on the existing `(post_id, user_id)` primary key.
- Post and comment deletion only set `is_deleted = TRUE`. Comment deletion checks comment authorship independently from post ownership, and a deleted parent makes comment reads and mutations unavailable without cascading child deletion.
- The JSON error contract is `400` for validation or unreadable JSON, `403` for a readable resource owned by another requester, and `404` for missing or soft-deleted targets. Success statuses are `201` create, `200` update/toggle, and `204` delete.
- Clean-volume PostgreSQL acceptance verified post/comment identity generation, requester ownership, Unicode title validation, requester-isolated likes, derived counts, retained soft-deleted rows, P2A read regression, and restoration to the seed baseline.

# Post Discovery Update (search + sort) — 2026-09-30

A `PRODUCT_DECISION` beyond the assignment: the list can be searched and
sorted by likes. The original contract is unchanged when the new parameters
are absent.

**API — `GET /api/posts`**

| Param | Rule |
| --- | --- |
| `limit` | 1–50, default 20 (unchanged); otherwise 400 `INVALID_LIMIT` |
| `cursor` | Opaque; must come from a page of the same `sort`, otherwise 400 `INVALID_CURSOR` |
| `sort` | `latest` (default) or `likes`; anything else 400 `INVALID_SORT` |
| `q` | Trimmed; blank means no search; at most 100 code points, otherwise 400 `INVALID_QUERY` |

The response stays `{ items, total, nextCursor }`, and `total` counts readable
posts that match `q`. `GET /api/posts?limit=10` is identical to
`?limit=10&sort=latest`.

**Ordering and cursors**

- **latest:** `created_at DESC, id DESC`, with the unchanged
  `(created_at, id)` row-value keyset and the existing `CursorCodec`. Latest
  cursors are byte-identical to before.
- **likes:** `effective_like_count DESC, created_at DESC, id DESC`, where
  `effective_like_count = base_like_count + post_likes rows`. The keyset is
  `(like_count, created_at, id) < cursor`.
  - The cursor is `PostLikeCursorCodec`, a tagged
    `base64url("likes|count|createdAt|id")`, so neither sort can read the
    other's cursor.
  - No OFFSET is used.
- Comment pagination (`PageRequestParser`, `CursorCodec`) is untouched; the
  shared limit check was only extracted as `parseLimit`.

**Search**

- Case-insensitive substring match over title or content:
  `ILIKE :pattern ESCAPE '\'`.
- The user's text is a bound parameter. `\`, `%` and `_` are escaped
  (`PostRepository.containsPattern`), so `100%` or `a_b` match literally.
- Authors are not searched, and soft-deleted posts never match.

**SQL shape.** Each page is two statements: the page itself (limit + 1 rows)
and the filtered `COUNT(*)`. There are no per-post round trips.

- **latest:** the existing query plus the search predicate. The like count,
  comment count and requester like are correlated per returned row after
  `LIMIT`.
- **likes:** a single statement. A `like_counts` CTE runs one `GROUP BY`
  over `post_likes`, and readable posts are joined to it. Then the search and
  keyset are applied, followed by `ORDER BY` and `LIMIT` into a `page` CTE.
  Comment count and requester like are attached to the page rows only; in
  `EXPLAIN ANALYZE` the comment subplan ran `loops=11` for an 11-row page.
- **Indexes:** none added. `ILIKE '%q%'` cannot use a B-tree index.
  `pg_trgm`, a migration and an extension are not justified for this
  dataset, and the likes order needs the computed count anyway.

**Known limitation — live like counts.** Likes ordering is deterministic for
a stable dataset, with no duplicates or skips across pages. There is no like
snapshot, though. If other requesters like or unlike between page requests, a
post can cross the cursor boundary:

- it may appear on two pages (the frontend renders each post ID once, without
  reordering);
- or it may be skipped until the list is refetched.

The requester's own likes refetch likes-ordered lists (below). A historical
snapshot was not built for this assignment.

**Frontend**

- **Query key:** `postKeys.list({ limit, sort, query })` becomes
  `["posts","list",{ limit, sort, query }]`, where `query` is trimmed or
  `null`. The cursor is the `pageParam`, so each sort/search combination is
  its own infinite query starting from page 1, and no cursor crosses lists.
- **Cancellation:** `getPosts(params, signal)` passes React Query's
  `AbortSignal` to `fetch`. A superseded or unmounted read is cancelled, and
  `request()` rethrows an abort as-is, so it never becomes `NETWORK_ERROR`.
  *(Later extended to `getPost` and `getComments`; see "Final ADR Status".)*
- **Search input:** `searchInput` updates on every keystroke. The committed
  `query` follows it after a 300 ms debounce, or immediately on Enter, clear
  or close.
- **Scroll reset:** a sort or search change scrolls back under the sticky
  toolbar when it is stuck.
- **Remembered view:** `lib/postListView.ts` keeps the last sort/search for
  in-app back navigation, as module memory like `lib/flash.ts`.

**Cache matrix** (`lib/query/postListCache.ts`; lists are no longer one
shared collection):

| Mutation | Edited in place (exact) | Invalidated (refetch from page 1 when shown) |
| --- | --- | --- |
| Create post | Prepended, with `total + 1`, in unfiltered latest lists only | Every other list (search match or likes position unknown) |
| Edit post | Loaded copies replaced everywhere; order is unchanged | Search lists (membership can change with the text) |
| Delete post | Row removed everywhere; `total − 1` in unfiltered lists and wherever the row was loaded | Search lists (total or membership where not loaded) |
| Like toggle | `isLiked`/`likeCount` on loaded copies everywhere | Likes-ordered lists (order may change) |
| Comment create/delete | `commentCount` on loaded copies everywhere | None (ordering and search membership are unaffected) |

# Deletion Consistency Model

One model covers posts, comments, and likes. It was verified against the running backend and PostgreSQL without any backend or schema change (`docs/VERIFICATION.md` "Deletion Consistency Evidence").

**1. Physical preservation.** Posts and comments are soft-deleted (`is_deleted = TRUE`); rows are never removed. Deleting a post does not cascade: its comments keep their own `is_deleted` value and its `post_likes` rows stay. A comment is only ever marked deleted by its author's delete.

**2. Visibility.**

```text
post readable    = NOT post.is_deleted
comment readable = NOT comment.is_deleted AND parent post readable
like effective   = parent post readable AND post_likes row exists
```

The children of a deleted post are dormant: they exist in the database but no product API reaches them.

**3. API semantics.** Readability is checked before ownership:

| State | Result |
| --- | --- |
| readable resource + owner | mutation allowed (`204` / `200` / `201`) |
| readable resource + non-owner | `403` |
| soft-deleted or never-existing resource | `404` |
| comment whose parent post is deleted | `404` |
| repeated DELETE | first `204`, then `404` (not idempotent-204) |

A deleted resource therefore never reveals that it existed through a `403`.

**4. Parent deletion.** After a post is deleted, every route under it returns `404`: GET/PATCH/DELETE, like toggle, comment list, comment create, and delete of an existing comment, for owners and non-owners alike. `PostReadService.getComments` checks `existsReadable` first, and `CommentRepository.findReadableMutationTargetForUpdate` joins the readable parent.

**5. Mutation serialization.** Post edit, delete, and like toggle, and comment create, each lock the readable post (`SELECT … FOR UPDATE`, `is_deleted = FALSE`). Comment delete locks the readable comment together with its readable parent (`FOR UPDATE OF p, c`). A post delete racing a child mutation is therefore serialized. Either the child mutation commits first and becomes dormant, or it runs after the delete, finds no readable parent, and returns `404`. A 15-round concurrent smoke test (delete racing comment create, like toggle, edit, and comment delete) produced only those outcomes, with no 5xx.

**6. Frontend consistency.** Nothing changes before the server confirms. After a `204`:
- Every cached post-list query (all are the same readable collection, differing only in page size) gets `total − 1`, whether or not the post is among the loaded pages. The row is removed where it is loaded. *(Superseded for search lists by the Post Discovery Update: lists now differ by sort and search, see its cache matrix.)*
- The deleted post's detail query and its descendant comment queries are evicted after the detail screen unmounts. TanStack partial key matching on `["posts","detail",id]` includes `[…,"comments",…]`.
- Navigation uses `router.replace("/")`, so Back does not return to the deleted detail.
- Keyset cursors stay valid because they are `(createdAt, id)` bounds, including when the deleted row was the cursor row.

## SSR Freshness and Failure Budgets — 2026-10-03

The two values have intentionally different responsibilities and are tuned
independently.

- **Seed freshness (`SEED_FRESH_MS = 5_000`):** React Query treats the SSR
  first-page cache entry as fresh through the observed hydration interval so it
  does not duplicate the server's work. Five throttled hard loads had seed
  ages around 1.65 s and no duplicate request at 5/15/30 seconds; 0 seconds
  duplicated all five. Five seconds is the shortest successful candidate.
  Freshness is not polling: it only makes a stale query eligible for normal
  triggers such as focus, remount, or explicit invalidation.
- **Server blocking (`SERVER_FETCH_TIMEOUT_MS = 2_000`):** this caps SSR's
  upstream wait. A server-only 1.8-second delay retained SSR content at 2.98 s
  median real-post LCP with 2 seconds, whereas 1.5 seconds fell back to CSR at
  4.04 s. A blackhole adds 0.54 s to fallback real-post LCP (4.05 → 4.59 s),
  the accepted bounded failure cost for retaining the measured slow SSR win.
- **Failure path:** a timeout has no server retry and returns `null`; the page
  responds HTTP 200 and hydrates the client list. That browser fallback then
  follows the separate classified query-retry policy (4xx none; network/5xx/
  unknown once). The two budgets must not be coupled.

# List Batch Size Decision — 2026-10-02

Evidence: `docs/PERFORMANCE.md` §13 (disposable 160-post dataset, 375×778, CPU 4×, Lighthouse devtools mobile throttling, fixed consumption depths of 30 and 45 posts).

- **Separate parameters:** with first-page SSR, the size of the server-rendered page (`SSR_SIZE`) and the size of each later cursor request (`CONTINUATION_SIZE`) are independent decisions; they affect first render and scrolling respectively and were measured separately (10/15/20 each).
- **Decision — keep 15/15:** SSR 10/15/20 differed in LCP only within measurement noise. Continuation 10 added requests and showed loading text even at reading speed; 20 gave no consistent gain over 15. With no measured benefit from different sizes, both stay at `POST_LIST_PAGE_SIZE = 15`. This is the most reasonable of the compared candidates under these conditions, not a universal optimum, and it was not chosen to split the seed's 39 readable posts into three requests.
- **Why the size is not derived from the total:** the total number of posts and one user's consumption depth are different quantities. Cursor pagination requests only what the user scrolls to (`limit + 1` rows per request), so 42, 1,000, or 100,000 posts give no reason for the page size to grow; the total only matters to someone who reads to the end. A fixed-depth comparison is the relevant criterion.
- **Mixed-size cost (not adopted):** a pair such as 15/20 is possible, but the key's `limit` would no longer describe every page, the first page and later pages would differ in size, the SSR-failure client fetch and refetch/invalidation paths would need a first-page branch, and cache tests would multiply. It was not adopted because no benefit was measured.
- **Open item:** the benchmark suggested that waits during fast scrolling depend more on how early the next page is requested than on page size. `rootMargin` (200px) is a follow-up to measure; it is unchanged. *(Later: measured; see List Prefetch Distance Decision.)*

# Client Query Retry Policy — 2026-10-03

- **Decision:** all client reads use the QueryClient default
  `retryOnceUnlessDeterministicClientError` from
  `frontend/lib/query/retryPolicy.ts`; individual query hooks do not duplicate
  a retry policy.
- **Classification:** completed `ApiError` 4xx responses return `false` on the
  first failure. Network errors (`ApiError` status 0), 5xx responses, and
  unknown query failures return `failureCount < 1`, which is exactly one retry
  because TanStack Query calls the predicate with zero for the initial failed
  attempt.
- **Why:** the installed v5.104.0 runtime's prior default made four attempts
  with 1 s, 2 s, and 4 s delays: a permanent read failure waited about seven
  seconds before UI could offer its existing manual retry. One retry preserves
  the observed fail-once automatic recovery at about one second; its default
  delay is not replaced with a product-specific value.
- **404 and UI:** a missing/soft-deleted post now follows the shared 4xx rule,
  so `usePostDetail` no longer owns a 404-only exception. The not-found UI
  remains immediate. List/comment continuation pages retain their loaded data
  and require their existing explicit retry after terminal failure.
- **Cancellation:** read query functions keep passing the supplied
  `AbortSignal` to `fetch`; `request()` rethrows an aborted error unchanged.
  TanStack Query cancellation stops its retryer before the policy can schedule
  another attempt, preserving no error UI and no stale overwrite.
- **Mutation boundary:** no mutation supplies `retry`, so TanStack Query's
  mutation default remains zero automatic retries. This keeps like toggle,
  post create/update/delete, and comment create/delete non-optimistic and
  server-confirmed.
- **Separate SSR budget:** the browser retry policy does not modify
  `SERVER_FETCH_TIMEOUT_MS`, SSR fallback, or the seed `staleTime`; server
  render failure handling is a distinct budget.

# Data Read Architecture — Decision Rationale

This section explains why the read path is shaped the way it is: the conditions it was built under, what the performance audit (`docs/PERFORMANCE.md`) measured, and the one change the measurements justified.

## 1. Starting conditions

The provided seed shaped the model more than any general scaling concern:

- 42 posts (3 soft-deleted) and 2,076 comments (81 soft-deleted); deletion flags come as `deletedPostIds` / `deletedCommentIds`.
- Posts carry `likeCount`, but there is **no per-user like history**.
- There is **no `commentCount` field**; the assignment requires it to be derived from comments, excluding deleted ones.
- Every post and comment has an ISO `createdAt` and a unique `id`, so `(createdAt, id)` gives a total, stable order. The seed contains no equal-timestamp ties, but the order does not depend on that.

The goals for the first implementation were:

- keep the database the single source of truth, with no second copy of any derived number;
- make drift between counts and rows impossible after create/delete;
- apply soft delete identically in list, detail, counts, and mutations;
- make infinite scroll a bounded read per request;
- avoid denormalization or caching layers the assignment's scale does not need.

## 2. Why `commentCount` is computed, not stored

`commentCount` and the comment `total` are computed at read time:

```sql
SELECT COUNT(*) FROM comments WHERE post_id = ? AND is_deleted = FALSE
```

There is no `posts.comment_count` column.

- The seed has no source value for such a column, so it would have to be derived anyway.
- A stored counter must be kept in step with comment create, soft delete, and post delete inside every mutation transaction. Any missed path causes drift, which would break `DEL-006`, `SEED-008`, and `SEED-009`.
- With a computed count, the comments table stays the only canonical source and mutation transactions stay simple.

The audit confirmed this choice. For the worst-case post #2 (1,411 readable comments), the COUNT takes ≈0.39 ms warm. At the API level, a comment page for a 2-comment post and for post #2 had the same latency (6.61 vs 7.28 ms median). **The normalized model is kept; `posts.comment_count` will not be added.**

## 3. Why likes are `base_like_count` + `post_likes`

The seed says how many likes a post has, but not who gave them. The model keeps both facts without inventing data:

- The seed number is stored as `posts.base_like_count` and never changes.
- Likes made while the application runs are rows in `post_likes (post_id, user_id)`. The primary key makes a duplicate like impossible.
- `likeCount = base_like_count + COUNT(post_likes rows)`, and `isLiked` is `EXISTS` for the requester.

This preserves the seed values exactly, supports requester-specific `isLiked`, and avoids fabricating per-user seed history (see ADR-005).

## 4. Why keyset instead of OFFSET pagination

Both collections are ordered `ORDER BY created_at DESC, id DESC` and continue from a cursor holding the last `(createdAt, id)` (ADR-006). The intent was:

- stable ordering, with `id` breaking equal timestamps;
- no shifted pages when new rows arrive during scrolling;
- no OFFSET-style work growing with depth, which suits comment infinite scroll.

The keyset contract was implemented correctly at the logical level. **Whether the cursor predicate actually bounded the index scan was not checked against PostgreSQL execution plans until the performance audit.**

## 5. Why a performance audit was run

Recomputing the seed distribution showed an extreme skew:

- 1,926 readable comments on readable posts; per post median 7, mean ≈49.4, max 1,411;
- post #2 alone holds ≈73.3 % of readable comments, and the top 5 posts hold ≈83.2 %.

The provided seed therefore includes a large, skewed workload, and it was used as a stress fixture. Rather than optimizing on intuition, the audit measured clean seed cost, API latency, SQL statement counts per request, `EXPLAIN (ANALYZE, BUFFERS)` at shallow and deep cursors, and a full traversal of post #2 (`docs/PERFORMANCE.md`).

## 6. What stays as it is

Measured and kept:

- query-time comment `COUNT` and per-page `total`;
- derived like count and requester `EXISTS`;
- the soft-delete model;
- the current composite indexes;
- single-transaction seed initialization;
- the normalized comments model.

Each costs sub-millisecond SQL or is not a meaningful part of API latency on the provided seed. Denormalized counters, caches, or extra indexes would add consistency risk and code for no measured benefit.

## 7. The one change the audit justified — applied

The cursor predicate was written as:

```sql
created_at < :cursorCreatedAt
OR (created_at = :cursorCreatedAt AND id < :cursorId)
```

It is semantically correct, but PostgreSQL applied it as a `Filter` after `Index Cond: post_id = …`. Each page walked the post's index range from the newest row. On post #2 the rows removed by the filter grew from 3 (first continuation) to 728 (middle) to 1,459 (deepest page), and buffers grew from 6 to 23 to 42. The pagination was keyset by contract but behaved like OFFSET in execution.

In a read-only experiment, the row-value form

```sql
(created_at, id) < (:cursorCreatedAt, :cursorId)
```

became part of the `Index Cond`. The deepest page dropped to 3–4 buffers and ≈0.11 ms (from ≈0.29 ms), with an identical result set.

This change was applied in `b86f668` to `PostRepository.findReadablePage` and `CommentRepository.findReadablePage`, and nothing else changed. It is valid because both columns are `NOT NULL`, both orderings are `created_at DESC, id DESC`, and the cursor is exactly `(createdAt, id)`. The reason is not the fraction of a millisecond saved: scan work that grew with page depth becomes a near-constant-cost index seek, which is what keyset pagination was chosen for.

Re-measured after the change: the row-value bound appears in `Index Cond` on post #2, and buffers stay at 3–4 from the first continuation to the last page (before: 6 → 23 → 42, with up to 1,459 rows filtered). All traversals returned identical results before and after, including a same-timestamp tie fixture with page boundaries inside the tie. API latency did not change measurably at this size, and the statement count per request is unchanged (`docs/PERFORMANCE.md` §12).

# ADR-003 — IDs: PostgreSQL identity columns that also accept seed IDs

**Status:** `DECIDED` — implemented. It was `PROVISIONAL` until the seed and schema existed.

## Decision

Use `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` for post/comment IDs.

- Seed import inserts the assignment-provided IDs explicitly.
- Newly created rows omit the ID and use the identity sequence.
- After first seed import, align the identity sequence above the maximum imported ID before accepting generated IDs.

## Implementation

- `V1__create_community_schema.sql` declares `posts.id` and `comments.id` as `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`.
- `PostRepository.insertSeedPost` and `CommentRepository.insertSeedComment` insert the seed IDs explicitly. Product creates omit the ID.
- `IdentitySequenceRepository.synchronizeWithSeededRows()` runs `setval(pg_get_serial_sequence(table, 'id'), MAX(id), true)` for both tables. It runs inside the `SeedInitializer` transaction, before the `seed_history` marker is written.

## Evidence

- Assignment evidence: seed IDs must be preserved exactly; IDs for new posts/comments may be assigned freely.
- PostgreSQL documents that `GENERATED BY DEFAULT AS IDENTITY` accepts explicit user-provided values while still generating values when an ID is omitted.
  - https://www.postgresql.org/docs/current/ddl-identity-columns.html
- PostgreSQL documents `pg_get_serial_sequence` for retrieving the sequence attached to an identity column.
  - https://www.postgresql.org/docs/current/functions-info.html
- PostgreSQL documents `setval` for aligning a sequence value.
  - https://www.postgresql.org/docs/current/functions-sequence.html

## Why this fits this assignment

This satisfies both competing requirements without maintaining a custom in-application ID allocator:

1. imported rows retain their original numeric IDs;
2. product-created rows receive generated numeric IDs.

## Risk and resolution

Explicit identity values do not by themselves guarantee that the backing sequence advances above those values. This was the reason for the explicit sequence sync above. Seed IDs are preserved exactly, and the first created post and comment receive non-conflicting IDs (`SEED-005`–`SEED-007`, `docs/VERIFICATION.md` V-003).

# ADR-004 — Data Model and Soft Delete

**Status:** `DECIDED` — implemented in `V1__create_community_schema.sql`. It was `PROVISIONAL` before P0, when a `deleted_at`-based shape was the working proposal (see "Evolution" below).

## Decision

Use three product tables plus one seed metadata table. This is the shipped schema:

```sql
CREATE TABLE posts (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(20) NOT NULL,
    content TEXT NOT NULL,
    author TEXT NOT NULL,
    base_like_count INTEGER NOT NULL CHECK (base_like_count >= 0),
    created_at TIMESTAMPTZ NOT NULL,
    is_deleted BOOLEAN NOT NULL DEFAULT FALSE
);

CREATE TABLE comments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    post_id BIGINT NOT NULL REFERENCES posts (id),
    content TEXT NOT NULL,
    author TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    is_deleted BOOLEAN NOT NULL DEFAULT FALSE
);

CREATE TABLE post_likes (
    post_id BIGINT NOT NULL REFERENCES posts (id),
    user_id TEXT NOT NULL,
    PRIMARY KEY (post_id, user_id)
);

CREATE TABLE seed_history (
    seed_key VARCHAR(64) PRIMARY KEY,
    imported_at TIMESTAMPTZ NOT NULL
);

CREATE INDEX posts_created_at_id_idx ON posts (created_at DESC, id DESC);
CREATE INDEX comments_post_id_created_at_id_idx ON comments (post_id, created_at DESC, id DESC);
```

- `title VARCHAR(20)`: PostgreSQL counts characters, matching the 20-code-point rule in `MutationValidator`.
- `author` and `user_id` are `TEXT`: requester names come from a header or cookie with no assignment-defined length, so no length was invented.
- There is no user table; ownership is `author == requester` (ADR-012).

## Evolution — initial proposal versus final schema

The pre-P0 proposal used `deleted_at TIMESTAMPTZ NULL` on posts and comments, `posts.updated_at`, `post_likes.created_at`, and placeholder `VARCHAR(...)` lengths. The final schema changed this:

| Initial proposal | Final | Reason |
| --- | --- | --- |
| `deleted_at TIMESTAMPTZ NULL` | `is_deleted BOOLEAN NOT NULL DEFAULT FALSE` | see "Why `is_deleted` rather than `deleted_at`" |
| `posts.updated_at` | not present | no API field or behavior reads an update time |
| `post_likes.created_at` | not present | likes are read only as existence and count |
| `author VARCHAR(...)` | `author TEXT` | no defined length to enforce |

## Evidence

- Assignment evidence: a separate user table is not required; ownership is `author == requester`.
- Assignment evidence: posts/comments must remain physically present after deletion but disappear from normal reads.
- PostgreSQL documents foreign keys as database-level referential integrity.
  - https://www.postgresql.org/docs/current/tutorial-fk.html
- PostgreSQL `timestamp with time zone` normalizes timestamp values internally and is suitable for absolute instants such as the assignment's ISO timestamps.
  - https://www.postgresql.org/docs/current/datatype-datetime.html

## Soft-delete rule

Normal product deletion is:

```text
is_deleted: FALSE -> TRUE
```

Seed rows listed in `deletedPostIds` / `deletedCommentIds` are inserted with `is_deleted = TRUE`. All normal list/detail/count queries treat `is_deleted = TRUE` as absent (and a comment as absent when its parent post is; see "Deletion Consistency Model").

This includes:

- post list,
- post detail,
- comment list,
- `commentCount`,
- mutation targets.

## Why `is_deleted` rather than `deleted_at`

`deleted_at` was the initial proposal because it would also record when a row was deleted. It was rejected for the shipped schema:

- The seed provides deletion **membership** (`deletedPostIds`, `deletedCommentIds`), not deletion **times**.
- Using `deleted_at` for imported deleted rows would mean inventing a timestamp that does not exist in the source data. The Architecture Review Finalization rules out deletion timestamps fabricated from seed data.
- No API field or screen shows when something was deleted.

A boolean records exactly the known fact. The accepted cost is that runtime deletions also keep no deletion time. An audit trail would need a separate decision.

## Index policy

Only query-shaped indexes justified by actual reads exist:

```text
posts_created_at_id_idx            posts(created_at DESC, id DESC)
comments_post_id_created_at_id_idx comments(post_id, created_at DESC, id DESC)
```

No speculative or partial indexes were added. The seed has only 42 posts and 2,076 comments. The performance audit (`docs/PERFORMANCE.md`) kept these two indexes and changed only the cursor predicate (see "Data Read Architecture" §7). If query plans later justified partial indexes on `is_deleted = FALSE`, they would be added with that evidence.

PostgreSQL documentation:
- multicolumn indexes: https://www.postgresql.org/docs/current/indexes-multicolumn.html
- partial indexes: https://www.postgresql.org/docs/current/indexes-partial.html

# ADR-005 — Likes: Historical Base Count + Requester Like Rows

**Status:** `DECIDED`

## Decision

Represent seed likes and requester likes separately:

```text
posts.base_like_count
post_likes(post_id, user_id)
```

API response:

```text
likeCount = base_like_count + count(post_likes for the post)
isLiked   = whether (post_id, current_user) exists in post_likes
```

## Evidence

- Assignment evidence: seed data contains `likeCount` but no like history.
- Assignment evidence: therefore `isLiked` starts false for every requester.
- Assignment evidence: like is a requester-specific toggle and the count must change with the toggle.

## Why this model

The seed count represents historical likes whose user identities do not exist in the input. Inventing users for those likes would fabricate data.

Keeping the historical count as a base value and storing only likes created through this application preserves every fact that actually exists in the seed.

It also avoids maintaining two mutable sources of truth (`like_count` counter + like rows) that could drift apart.

## Trade-off accepted

`likeCount` requires an aggregate over requester-generated likes. At this assignment's data size, correctness and clarity are more valuable than denormalizing a mutable counter.

# ADR-006 — Pagination: Cursor/keyset pagination with deterministic ordering

**Status:** `DECIDED`

## Decision

Use cursor-based pagination for both posts and comments.

Canonical order:

```text
ORDER BY created_at DESC, id DESC
```

The cursor represents the final `(created_at, id)` pair from the current page. The API keeps the required `items` and `total` fields and adds `nextCursor`.

Implemented wire contract:

```text
GET /api/posts?limit=20&cursor=<opaque>
GET /api/posts/{postId}/comments?limit=20&cursor=<opaque>

default limit: 20
valid limit: 1..50
omitted cursor: first page
invalid limit or cursor: HTTP 400
```

The opaque cursor is URL-safe Base64 without padding over `<exact Instant text>|<id>`. Its timestamp is not reduced to epoch milliseconds. The decoder accepts only the canonical encoding and valid positive IDs. Repositories use `LIMIT + 1`, return at most the requested limit, and never use `OFFSET`.

Example conceptual response:

```json
{
  "items": [],
  "total": 39,
  "nextCursor": "opaque-value"
}
```

## Evidence

- Assignment evidence: posts and comments are newest-first and must be loaded in pages rather than all at once.
- PostgreSQL states that `LIMIT` should be paired with an `ORDER BY` that constrains rows into a unique order, otherwise page subsets can be unpredictable.
- PostgreSQL also states that rows skipped by a large `OFFSET` still have to be computed.
  - https://www.postgresql.org/docs/current/queries-limit.html

## Why this fits this assignment

Infinite scrolling and concurrent creation are a better match for a position-based cursor than a page number. Adding `id` as a tie-breaker makes ordering deterministic even when multiple rows have the same timestamp.

## Why not offset pagination

Offset pagination would be acceptable for the tiny seed from a raw performance perspective and is simpler to explain. It was not selected because insertion of a newer row can shift later offsets while the user is scrolling, increasing the chance of duplicates/skips.

## Trade-off accepted

The backend must encode/decode a cursor and the client cannot jump directly to arbitrary page numbers. The product has no page-number UI, so that cost is irrelevant here.

# ADR-010 — Infinite Scroll Trigger: `IntersectionObserver`

**Status:** `DECIDED` — implemented. It was `PROVISIONAL` at P0, while pagination and server state were unresolved.

## Decision

Use a sentinel element observed with `IntersectionObserver` to request the next TanStack Query page.

Guard the callback with `hasNextPage` and `isFetchingNextPage`.

## Implementation

- `frontend/lib/hooks/useInfiniteScrollTrigger.ts` observes a sentinel with `rootMargin` `0px 0px 200px 0px` by default. It does not poll scroll positions. *(Later: the post list passes 500px; comment continuation keeps the default. See List Prefetch Distance Decision.)*
- On the first intersection it disconnects and calls `onIntersect` once, so each enabled cycle sends one request. A new observer is created when `enabled` turns true again. That observer reports the current intersection, so a sentinel still visible after a page loads continues without another scroll.
- Callers guard `enabled` with request state:
  - `PostListScreen`: `data !== undefined && hasNextPage && !isFetchingNextPage && !isFetchNextPageError`.
  - `CommentSection`: the same, plus `expanded`, so nothing loads before “더보기”.
- A failed next page leaves the trigger disabled until an explicit retry, so it does not loop.

## Evidence

- MDN documents `IntersectionObserver` as asynchronously observing when a target intersects a viewport/ancestor and notes that it avoids continuous main-thread visibility polling.
  - https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API

## Why this fits this assignment

The UI requirement is “load the next page when the user reaches the end,” not “react to every scroll position.” A sentinel intersection is the direct browser primitive for that condition.

## Trade-off accepted

Observer lifecycle must be handled correctly, but this is simpler and less error-prone than custom scroll-position calculations.

# ADR-012 — Backend Validation, Ownership, Transactions, and Error Handling

**Status:** `DECIDED`

## Decision

### Validation

Backend request DTOs use a small explicit validator without adding a validation dependency:

- title: non-null, nonblank, and at most 20 Unicode code points via `codePointCount`
- post content: non-null and nonblank
- comment content: non-null and nonblank, with no maximum length added

Blank checks are validation-only; accepted values are stored without automatic trimming.

Frontend validation mirrors these rules for UX, but backend validation is authoritative.

### Ownership

Resolve requester deterministically:

```text
x-user-id header > x-user-id cookie > apr_tester
```

The precedence is an implementation decision because the assignment allows header or cookie but does not specify conflict precedence.

Ownership checks live in the service/application layer, not only in UI visibility.

### Transactions

Use service-level `@Transactional` around mutation methods. Readable targets are locked before ownership-sensitive changes, and like toggles serialize on the post row while the existing composite primary key preserves requester uniqueness.

### Errors

Use `@RestControllerAdvice` for consistent JSON errors.

Implemented status semantics:

```text
400 validation / malformed input
403 authenticated-by-assignment requester does not own resource
404 missing or soft-deleted resource
201 successful creation
200 successful read/update/toggle
204 successful delete
```

The assignment explicitly allows status-code selection as long as behavior is correct.

## Evidence

- Repository evidence: `MutationValidator` performs dependency-free null/blank and Unicode code-point validation, while `ApiExceptionHandler` maps unreadable JSON to the shared error body.
- Spring Framework documents declarative `@Transactional` support.
  - https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/declarative/annotations.html
- Spring MVC documents `@RestControllerAdvice` as controller-wide exception handling that renders response bodies.
  - https://docs.spring.io/spring-framework/reference/6.2/web/webmvc/mvc-controller/ann-advice.html

## Trade-off accepted

This creates a small amount of explicit DTO/error mapping code, but keeps validation, authorization, and HTTP semantics out of repository code and prevents the frontend from becoming the security boundary.

# ADR-013 — Seed Initialization: transactional, idempotent, source-preserving

**Status:** `DECIDED` — implemented. It was `OPEN` at P0, when the migration mechanism and the startup hook did not exist yet.

## Decision

Use the runtime `APP_SEED_PATH` as the only assignment seed source.

Final flow (`backend/.../seed/SeedInitializer.java`, an `ApplicationRunner` that runs after Flyway, with `run()` annotated `@Transactional`):

```text
Flyway schema ready
    ↓
SeedInitializer.run() — one transaction:
  seed_history has "assignment-v1"?
    yes → register readiness after commit, stop
    no  → read seed.json
          insert posts with explicit IDs (deletedPostIds → is_deleted = TRUE)
          insert comments with explicit IDs (deletedCommentIds → is_deleted = TRUE)
          align post/comment identity sequences
          record seed_history marker "assignment-v1"
          register readiness after commit
    ↓
commit → SeedReadiness opens /health
```

Two changes from the initial proposal:

- Sequence alignment moved inside the transaction, before the marker.
- The readiness gate was added; see "Resolution" below.

Do not re-apply seed values on every restart because doing so could overwrite user edits made after first boot.

## Evidence

- Assignment evidence: data must be queryable after application startup and repeated startup must not duplicate seed data.
- Provided README: `seed/` is mounted read-only at `/seed` via `APP_SEED_PATH`, while PostgreSQL data persists in a named volume.
- Spring Boot 3.5 documents database initialization ordering and mechanisms.
  - https://docs.spring.io/spring-boot/3.5/how-to/data-initialization.html

## Why use a seed marker rather than only `COUNT(*) > 0`

Table non-emptiness does not prove that the assignment seed was completely and successfully imported. A specific marker written only after the import transaction succeeds gives the operation explicit semantics.

## Original question and resolution

*Original question (P0):* which lifecycle hook guarantees the seed has finished before the application counts as ready, without breaking the required `/health` behavior?

**Problem observed:** with an `ApplicationRunner` alone, Tomcat and the DB come up before the runner's seed transaction commits. The starter `/health` only checked DB reachability, so on a clean start `/health` returned 200 while `GET /api/posts` still reported `total` 0. Compose could then mark the backend healthy and start the frontend against an unseeded database.

**Resolution:**

- `SeedReadiness.markReadyAfterCommit()` registers a `TransactionSynchronization` whose `afterCommit()` sets the ready flag. It is called on both paths: a fresh import, and a restart that finds the marker already present.
- `HealthController` returns 503 `{"status":"starting","db":"up"}` until the flag is set. After that it keeps the starter contract: 200 `{"status":"ok","db":"up"}` when the DB is reachable.
- Compose's `/health` healthcheck therefore marks the backend healthy only after the seed data is committed and queryable.
- If the import fails, the transaction rolls back, no marker is written, readiness never opens, and the next start retries the full import.

**Trade-off accepted:** the first clean start does not report healthy until the seed import finishes (about 0.9 s on the provided seed). Readiness is an in-memory flag per process.

Evidence: `docs/VERIFICATION.md` "P8-A First-Boot Readiness Investigation" and V-001/V-003.

# 2. Backend Structure

**Status:** `DECIDED` — this is the shipped package layout under `backend/src/main/java/com/apr/community/`.

The structure stays shallow and feature-oriented, with no interfaces or abstractions that lack a concrete second implementation.

```text
com/apr/community/
├── CommunityApplication, CorsConfig        # starter
├── HealthController                        # starter path; readiness-gated (ADR-013)
├── common/
│   ├── error/        ApiErrorResponse, ApiException, ApiExceptionHandler
│   ├── pagination/   CursorCodec, CursorPosition, PageRequest, PageRequestParser, PageResponse
│   ├── requester/    RequesterResolver
│   └── validation/   MutationValidator
├── post/
│   ├── PostController                      # /api/posts/**, incl. nested comment list/create
│   ├── PostReadService                     # reads: list (latest/likes/search), detail, comments
│   ├── PostMutationService                 # create/update/delete, like toggle; ownership + transactions
│   ├── PostListRequest, PostListRequestParser, PostSort
│   ├── PostLikeCursor, PostLikeCursorCodec
│   └── PostMutationRequest, PostResponse, LikeToggleResponse
├── comment/
│   ├── CommentController                   # DELETE /api/comments/{commentId}
│   ├── CommentMutationService              # comment create/delete; ownership + transactions
│   └── CommentCreateRequest, CommentResponse
├── persistence/
│   ├── PostRepository, CommentRepository, PostLikeRepository
│   └── IdentitySequenceRepository, SeedHistoryRepository
└── seed/
    ├── SeedInitializer (ApplicationRunner), SeedReadiness
    └── SeedData, SeedDataReader
```

Schema: `backend/src/main/resources/db/migration/V1__create_community_schema.sql`.

Layer responsibility:

```text
Controller  HTTP translation only (request parsing, requester resolution, status codes)
Service     validation, ownership, transactions, domain rules
Repository  SQL and row mapping (JdbcClient), no HTTP semantics
Common      cross-cutting rules: requester, validation, cursor/paging, JSON errors
```

**Evolution from the pre-P0 proposal.** The proposal sketched a single `PostService` and `CommentService`, a `like/` package, `dto/` folders, and `SeedLoader`/`SeedService`. The final code differs:

- Post reads and mutations are separate services, because reads carry the pagination, sort and search work while mutations own locking and ownership.
- The like toggle lives in `PostMutationService`, because it locks the post row like the other post mutations.
- All SQL repositories sit together in `persistence/`.
- Request/response records sit beside their controllers; there is no `dto/` directory.
- Seeding is `SeedInitializer` plus `SeedReadiness`.

Repository interfaces were not introduced. Add an interface only when it creates an actual testing or implementation boundary.

    ├── api/          client.ts (request), community.ts (endpoints), types.ts

    └── avatar.ts, flash.ts, formOrigin.ts, postId.ts, postListView.ts, requester.ts, routes.ts

Principles:

- route files compose screens;
- feature code owns product behavior;
- one shared API client owns base URL, JSON handling, and `credentials: "include"`;
- TanStack Query owns remote state;
- local component state owns ephemeral presentation state.

**Evolution from the pre-P0 proposal.** The proposal grouped features by entity (`posts/`, `comments/`, `likes/`) and planned a shared `components/` folder. The final code groups features by screen flow (`post-list`, `post-detail`, `post-form`), because each screen owns its queries, mutations and states. No `components/` folder was created, because no visual primitive was shared widely enough to justify one. Styles are co-located `.module.css` files.

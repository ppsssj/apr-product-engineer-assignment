# 아키텍처 결정 기록

이 문서는 APR Product Engineer 과제의 architecture 선택과 그 이유를 기록합니다.

기준 문서는 `ASSIGNMENT.md`입니다. 이 문서는 요구사항을 **어떻게, 왜** 구현했는지 설명할 뿐이며, 요구사항을 약화하거나 다르게 해석하지 않습니다.

## 근거 정책

영향이 큰 결정은 사실과 판단을 분리해 기록합니다.

근거 유형:

- **Assignment evidence** — `ASSIGNMENT.md`에 명시된 요구사항.
- **Starter evidence** — 제공된 starter repository에서 확인한 동작·설정.
- **Official documentation** — framework·database·browser의 1차 공식 문서.
- **Engineering judgment** — 위 근거에서 내린 판단. 대안과 trade-off를 함께 적습니다.

결정 상태:

- `DECIDED` — 구현하기에 충분한 근거가 있는 선택.
- `PROVISIONAL` — 현재 선호하는 선택이지만 repository·design 점검 결과에 따라 바뀔 수 있음.
- `OPEN` — 결정이 나기 전까지 해당 영역을 구현하지 않음.

공식 출처가 있으면 blog 글이나 AI가 생성한 주장을 근거로 인용하지 않습니다.

- **Read 취소:** `usePostList`, `usePostDetail`, `useComments`는 TanStack Query의 `AbortSignal`을 `getPosts`/`getPost`/`getComments`를 거쳐 `request()`까지 전달합니다. abort는 `NETWORK_ERROR`로 바꾸지 않고 그대로 다시 throw합니다.

## 현재 검증 구조

한 종류의 test로 모든 위험을 덮지 않고, runtime 경계를 따라 검증을 쌓았습니다.

```text
JUnit/Mockito + Vitest
  → PostgreSQL Testcontainers integration
  → production Docker Compose smoke
  → selected Chromium Playwright regression
```

- Backend unit/service test는 database 없이 controller 계약, validation, requester 판별, cursor codec, transaction 판단을 검증합니다.
- Testcontainers 6 suites / 31 tests는 실제 Flyway migration과 `SeedInitializer`를 거친 PostgreSQL 16에서 실행됩니다. schema 제약, repository SQL, keyset·검색 동작, 영속성, 동시 locking을 다룹니다.
- `full-stack-smoke`는 backend·frontend job이 통과한 뒤 production Compose stack을 build·기동하고 health, API, SSR, seed history, build 시점에 고정된 browser API base를 확인합니다.
- 커밋된 Playwright 3 flows는 그 stack을 대상으로 Chromium 375×778에서 실행됩니다. 검색·좋아요·mobile 불변식, 댓글 더보기/재방문 동작, 삭제 dialog의 keyboard focus를 지킵니다. 더 넓은 수동·runtime 근거를 대체하지는 않습니다.

정확한 명령, 현재 수치, CI 근거와 자동화 한계는 `docs/VERIFICATION.md`에, 결정의 변화 과정은 `docs/ENGINEERING_NOTES.md`에 둡니다.

# P0 저장소 점검 — 2026-09-29

이 section은 아래 "Pre-P0 근거 경계"를 대체했습니다. 이 repository에서 직접 관찰한 사실과, 그 결과 각 제안 결정이 어떤 상태가 되었는지만 기록하며 product 동작은 구현하지 않았습니다.

*시점 기록:* 아래 사실은 구현을 시작하기 전 제공된 starter의 상태입니다(예: 당시의 유일한 Java source, 아직 선언되지 않았던 Flyway와 `typecheck` script). 상태 조정 표의 상태도 P0 기준입니다. 현재 상태는 위 "최종 ADR 상태"를 보세요.

## 저장소 사실 (P0 당시)

### Backend

- `backend/build.gradle`은 Gradle Groovy, Java toolchain 17, Spring Boot `3.5.0`, Spring dependency management `1.1.7`을 사용했습니다. *(이후: 보안 dependency patch로 현재 Spring Boot는 `3.5.16`입니다.)*
- 선언된 runtime/application dependency는 `spring-boot-starter-web`, `spring-boot-starter-jdbc`, runtime PostgreSQL JDBC였습니다. Test는 `spring-boot-starter-test`와 명시적 Mockito agent를 사용했습니다. JPA, Flyway, Liquibase, validation starter는 선언되어 있지 않았습니다.
- base package는 `com.apr.community`였습니다. 당시 Java source는 `CommunityApplication`, `HealthController`, `CorsConfig`뿐이었고 domain, service, repository, schema, migration source는 없었습니다.
- `application.yml`은 datasource URL/user/password override를 받고, local PostgreSQL 기본 port를 `15432`로, server port를 `8080`으로 두며, `APP_SEED_PATH`(기본값 `../seed/seed.json`)를 읽었습니다.
- `HealthController`는 `GET /health`에서 datasource connection을 얻어 HTTP 200과 `status: ok`, `db: up`을 반환했고, connection 실패 시 HTTP 503을 반환했습니다. *(이후: seed readiness gate가 추가되었습니다. ADR-013 참고.)* `CorsConfig`는 설정된 localhost/127.0.0.1 origin pattern, credential, 필요한 HTTP method를 허용했습니다.

### Frontend

- `frontend/package.json`은 Next.js `15.4.6`, React/React DOM `19.1.0`, TypeScript `^5`를 사용했습니다. `package-lock.json`이 있어 package manager는 npm입니다. *(이후: dependency 업데이트로 현재 Next.js는 `15.5.27`, React/React DOM은 `19.1.9`입니다.)*
- App Router(`app/`의 `layout.tsx`, `page.tsx`)를 사용했습니다. script는 `dev`, `build`, `start`뿐이었고 lint나 독립 typecheck script는 없었습니다.
- styling framework, server-state library, data-fetching library는 선언되어 있지 않았습니다. `globals.css`는 `public/fonts/PretendardVariable.woff2`의 Pretendard Variable font face와 base style을 정의했습니다.
- `frontend/app/dev-user/page.tsx`가 있었고, client에서 `x-user-id` cookie를 설정·삭제하며 user 선택 시 `/`로 redirect했습니다. 이 page는 수정하지 않는 대상이며 현재도 그대로입니다.
- Public asset은 `avatar-1.png`, `avatar-2.png`, `avatar-3.png`, Pretendard Variable과 그 OFL license였습니다.

### Runtime과 Seed

- `docker-compose.yml`은 `db`, `backend`, `frontend`를 정의했습니다. DB는 `postgres:16-alpine`이고 named volume `dbdata`를 쓰며 `${DB_PORT:-15432}`를 노출했습니다. Backend는 DB health를 기다리고 `./seed:/seed:ro`를 mount하며 `APP_SEED_PATH=/seed/seed.json`을 사용하고 `${BACKEND_PORT:-8080}`을 노출하며 `/health` healthcheck를 가졌습니다. Frontend는 backend health를 기다리고 `${FRONTEND_PORT:-3000}`을 노출하며, build 시점 `NEXT_PUBLIC_API_BASE_URL`과 container 내부 전용 `API_BASE_URL=http://backend:8080/api`를 받았습니다.
- `seed/seed.json`은 top-level key `posts`, `comments`, `deletedPostIds`, `deletedCommentIds`를 가진 유효한 JSON입니다. 고유 post ID 42개(1–42), 고유 comment ID 2,076개(1–2,076), 삭제 post ID 3개, 삭제 comment ID 81개를 담고 있습니다. 모든 삭제 ID는 대응하는 seed record를 가리킵니다.
- Post field는 `id`, `title`, `content`, `likeCount`, `author`, `createdAt`이고 comment field는 `id`, `postId`, `content`, `author`, `createdAt`입니다. 관찰한 모든 field는 non-null입니다. ID와 `likeCount`는 number, 나머지는 string입니다. `commentCount`는 없습니다. timestamp는 ISO UTC 문자열입니다. 모든 comment는 존재하는 post를 참조하며, post 10과 23에는 comment가 없습니다.
- `design/`은 있었지만 file이 없었습니다. 따라서 P0 동안 repository 안의 Figma asset과 screenshot/reference image는 `MISSING`이었습니다. 이후 공식 Figma URL이 제공되었고, 아래 "Figma Design Audit 반영"에 기록했습니다.

## 확인한 Starter 계약

- 과제가 정한 수정 불가 `/dev-user`, `GET /health` HTTP 200, CORS/credential 요청, read-only seed mount, port override 계약은 모두 대응하는 starter code/설정이 있었습니다.
- health endpoint가 DB 연결 가능 여부를 확인하므로, backend healthcheck는 의도적으로 사용 가능한 DB connection에 의존합니다.
- 점검한 starter 설정과 위 계약 사이에 모순은 없었습니다. 다만 P0 동안 runtime 동작 자체를 실행해 보지는 않았습니다.

## 확인한 외부 근거

- [Spring JDBC 6.2 documentation](https://docs.spring.io/spring-framework/reference/6.2/data-access/jdbc.html): application code가 SQL을 제공하고 Spring JDBC 추상화가 connection/resource lifecycle을 맡는다는 점을 확인했습니다.
- [Spring Boot 3.5 database-initialization documentation](https://docs.spring.io/spring-boot/3.5/how-to/data-initialization.html): schema 초기화 방식을 하나만 쓰도록 권장하고, PostgreSQL에서 Flyway를 쓰려면 database 전용 Flyway module이 classpath에 있어야 한다고 설명합니다.

여기 나열하지 않은 기존 외부 인용은 이 P0 점검에서 `NOT_EXTERNALLY_VERIFIED`로 남겼으며, repository 사실로 취급하지 않았습니다.

# Architecture Review 확정 — 2026-09-29

**검토 상태:** `COMPLETE`
**기준 기록:** 당시 이 section은 이전 제안 ADR text·상태 label과 충돌할 때 우선했습니다. 구현 방향만 확정했고 dependency, schema, product code는 추가하지 않았습니다. *(현재 ADR-001~ADR-013 본문은 이 확정 내용을 구현 결과에 맞춰 반영한 것입니다.)*

## 공통 제약과 불변식

- **Assignment evidence:** Java 17/Spring Boot 3.x, Next.js 15 App Router, PostgreSQL, 전체 stack `docker compose up`, soft delete, requester별 좋아요, 범위가 정해진 pagination, seed ID 보존, 수정 불가 `/dev-user`/`GET /health` 계약은 필수입니다.
- **Repository evidence(당시):** JDBC와 PostgreSQL은 이미 선언되어 있었고 JPA, migration 도구, state/data library, UI library는 없었습니다. seed는 post 42개, comment 2,076개, 명시적 ID, 집계 `likeCount`를 담고 있으며 과거 user별 like 데이터와 `commentCount`는 없습니다.
- **범위 불변식:** user table, 지어낸 과거 like user, seed 데이터로 만들어 낸 삭제 timestamp, 추측성 분산 architecture, 불필요한 추상화 layer를 두지 않습니다.

## 확정 결정

| 결정 | 상태 | 결정과 적합성 | 검토한 대안 / 수용한 trade-off | 구현 검증 방법 |
| --- | --- | --- | --- | --- |
| Persistence | `DECIDED` | Spring JDBC `JdbcClient`와 명시적 SQL repository를 사용합니다. 선언된 JDBC starter와 호환되고 soft delete, ownership, 집계 count, 좋아요, pagination query가 코드에 그대로 드러납니다. | JPA/Spring Data JPA 추가. 선언되지 않은 ORM dependency가 늘고 과제의 query별 작업도 줄어들지 않아 제외했습니다. | CRUD, soft delete filter, ownership, row mapping을 compile·integration test합니다. |
| Schema migration | `DECIDED` | 버전 관리되는 schema migration에만 Flyway를 씁니다. 제공된 JSON은 migration data로 복제하지 않고 application code에서 읽습니다. 영속 DB volume은 재시작 간 schema 이력이 필요합니다. | `schema.sql`. 더 단순하고 dependency가 없지만 schema 변화를 덜 명시적으로 다룹니다. Flyway는 dependency와 PostgreSQL module이 추가되는 비용이 있습니다. | 빈 volume과 재시작 test로 migration이 한 번만 적용되고 schema 이력이 안정적인지 확인합니다. |
| Seed lifecycle | `DECIDED` | Flyway 이후 `ApplicationRunner`로 idempotent JSON import를 실행합니다. 명시적 ID로 insert하고, 이후 user 변경을 보존하며, transaction이 성공한 뒤에만 import 완료를 기록합니다. | 매 기동마다 row를 reset/update. user가 만들거나 수정한 상태를 덮어쓰므로 제외했습니다. | 기동/재시작 test: 중복 record 없음, 삭제 ID는 계속 삭제 상태, sequence가 새 row를 허용. |
| IDs | `DECIDED` | `BIGINT GENERATED BY DEFAULT AS IDENTITY`를 씁니다. 명시적 seed ID를 import한 뒤 각 sequence를 seed 최댓값 위로 맞춥니다. | Application 측 ID 할당. 과제에 가치 없는 추가 상태라 제외했습니다. | seed ID가 그대로 유지되고, 처음 생성한 post/comment가 충돌 없는 ID를 받습니다. |

| Pagination | `DECIDED` | `(created_at DESC, id DESC)` 순서의 cursor/keyset pagination을 쓰고, 필수 `items`/`total`을 유지하며 `nextCursor`를 추가합니다. 동시에 생성·삭제가 일어나는 최신순 infinite scroll에 맞습니다. | Offset pagination. 더 단순하지만 scroll 중 위치가 밀릴 수 있고, 별도 total count도 여전히 필요합니다. | 범위가 정해진 page 요청이 결정적이고 인접 page 사이에 중복·누락이 없습니다. |

| Styling | `DECIDED` | Pretendard/reset/token은 기존 `globals.css`에, component/page style은 CSS Modules에 둡니다. 이 mobile 과제에는 UI framework가 필요 없습니다. | Tailwind나 UI kit. 둘 다 설치되어 있지 않고 설정·dependency 범위가 늘어 제외했습니다. | design asset이 제공되면 Next build와 375px visual review. |

| Relative time | `DECIDED` | 작은 threshold utility 뒤에서 native `Intl.RelativeTimeFormat("ko", { numeric: "always" })`를 씁니다. seed의 UTC timestamp는 절대 시각으로 적합합니다. | Date library. 필요한 것이 formatting뿐이라 제외했습니다. | 고정 clock unit test로 초/분/시간/일과 한국어 숫자 출력을 확인합니다. |

Bean Validation dependency와 error payload type은 구현 세부로 남깁니다. | UI에서만 권한 확인. 직접 API 호출을 막아야 하므로 제외했습니다. | 직접 API test로 잘못된 요청과 다른 user의 mutation이 거부되고, 허용된 mutation이 원자적으로 반영됨을 확인합니다. |

## 외부 근거

- **Spring Framework 6.2 — [JdbcClient](https://docs.spring.io/spring-framework/reference/data-access/jdbc/core.html):** `JdbcClient`는 Spring Framework 6.1부터 제공되는 fluent 통합 JDBC query/update API입니다. 선언된 Spring Boot 3.5 JDBC 경로를 뒷받침합니다.
- **Spring Boot 3.5 — [Database Initialization](https://docs.spring.io/spring-boot/3.5/how-to/data-initialization.html):** schema 초기화 방식을 하나만 쓰도록 권장합니다. Flyway는 기동 시 실행되며, PostgreSQL은 database 전용 Flyway module이 필요합니다.
- **Spring Boot 3.5 — [SpringApplication](https://docs.spring.io/spring-boot/3.5/reference/features/spring-application.html):** `ApplicationRunner`는 `SpringApplication.run`이 끝나기 직전에 실행되므로 1회성 기동 bootstrap 작업에 맞습니다.
- **PostgreSQL 16 — [Identity Columns](https://www.postgresql.org/docs/16/ddl-identity-columns.html):** `GENERATED BY DEFAULT` identity column은 명시적으로 넣은 값을 허용하고, 값이 없으면 생성합니다.
- **PostgreSQL — [LIMIT and OFFSET](https://www.postgresql.org/docs/current/queries-limit.html):** page 부분집합에는 결정적 정렬이 필요하고, 건너뛴 offset row도 계산된다고 설명합니다. keyset trade-off의 근거입니다.
- **TanStack Query v5 — [Infinite Queries](https://tanstack.com/query/latest/docs/framework/react/guides/migrating-to-v5):** infinite query는 paginated page data를 모델링하고, v5는 `maxPages`로 보관 page 수를 제한할 수 있습니다.
- **Next.js — [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components):** page/layout은 기본이 Server Component이고, Client Component는 browser API, event, effect, state에 적합합니다.
- **MDN — [Intersection Observer API](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API):** 비동기 교차 관찰을 제공하며 infinite scroll을 사용 사례로 명시합니다.
- **MDN — [Intl.RelativeTimeFormat](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/RelativeTimeFormat):** native locale별 상대 시간 formatter를 설명합니다.

# P2A Read API 구현 반영 — 2026-09-29

- Requester 판별은 하나의 `RequesterResolver`가 `x-user-id` header > `x-user-id` cookie > `apr_tester`라는 결정적 우선순위로 수행합니다. 빈 값이나 공백뿐인 값은 없는 것으로 보며, user table은 만들지 않습니다.
- 두 read collection 모두 선택적 `limit`과 `cursor`를 받습니다. 기본 limit은 20, 허용 범위는 1–50이며, 잘못된 limit이나 cursor는 HTTP 400 JSON error를 반환합니다.
- 기준 순서는 `(created_at DESC, id DESC)`입니다. 다음 page 조건도 같은 timestamp·ID 쌍을 비교하고, repository는 `OFFSET` 없이 `limit + 1`행을 가져와 `nextCursor` 존재 여부를 판단합니다.
- Opaque cursor payload는 정확한 `Instant` 문자열과 숫자 ID를 `|`로 이은 값이며, padding 없는 URL-safe Base64로 encode합니다. decode 시 non-canonical Base64, 잘못된 timestamp, 0 이하·잘못된 ID, 형식이 깨진 payload를 거부합니다.
- P2A endpoint는 `GET /api/posts`, `GET /api/posts/{postId}`, `GET /api/posts/{postId}/comments` 세 개뿐이었습니다. post page row는 `likeCount`, requester별 `isLiked`, 읽을 수 있는 `commentCount`를 범위가 정해진 SQL query 하나에서 계산하고, 별도 count query가 전체 `total`을 제공합니다.
- 없는 post와 soft delete된 post는 같은 404 JSON 계약을 반환합니다. 댓글 read는 먼저 읽을 수 있는 parent post를 요구합니다. P2A 시점에는 mutation validation과 ownership 강제를 의도적으로 P2B로 미뤘습니다.

# P2B Mutation API 구현 반영 — 2026-09-29

- 필수 mutation route 6개는 각자 좁은 request/response record를 쓰며 P2A read 계약은 바꾸지 않습니다. post 생성/수정은 하나의 명시적 validator를 공유합니다. 제목 길이는 `String.codePointCount`로 재고, blank 확인은 저장 값을 trim하지 않으며, 댓글 내용에는 임의의 최대 길이를 두지 않습니다.
- 빈 댓글 거부는 `PRODUCT_DECISION`입니다. 과제는 댓글 생성을 요구하지만 blank 규칙은 명시하지 않습니다. nonblank 요구로 빈 댓글 저장을 막되 길이 제한은 추가하지 않았습니다.
- `PostMutationService`와 `CommentMutationService`가 ownership과 transaction의 최종 경계입니다. repository는 SQL primitive만 노출하고 HTTP status 의미를 담지 않습니다.
- 모든 mutation method는 service-level `@Transactional`입니다. 읽을 수 있는 대상 row를 ownership 확인이나 여러 단계 변경 전에 잠그며, 좋아요 toggle은 읽을 수 있는 post row에서 직렬화하고 기존 `(post_id, user_id)` primary key에 기댑니다. *(정확히는 post 생성에는 잠글 기존 row가 없고, 댓글 생성은 parent post를 잠급니다. 현재 method별 lock 대상은 ADR-012 "Transactions"에 정리했습니다.)*
- post와 comment 삭제는 `is_deleted = TRUE`로만 설정합니다. 댓글 삭제는 post ownership과 별개로 댓글 작성자를 확인하고, parent가 삭제되면 하위 댓글을 cascade 삭제하지 않은 채 댓글 read·mutation을 사용할 수 없게 합니다.
- JSON error 계약은 validation·읽을 수 없는 JSON은 `400`, 다른 requester가 소유한 읽을 수 있는 resource는 `403`, 없거나 soft delete된 대상은 `404`입니다. 성공 status는 생성 `201`, 수정/toggle `200`, 삭제 `204`입니다.
- 빈 volume PostgreSQL acceptance에서 post/comment identity 생성, requester ownership, Unicode 제목 validation, requester별로 분리된 좋아요, 파생 count, soft delete 후 남는 row, P2A read 회귀, seed baseline 복원을 확인했습니다.

# P3 Frontend 기반 반영 — 2026-09-29

- **Server state (ADR-007):** 추가한 production dependency는 `@tanstack/react-query` 하나이며 `package-lock.json`은 5.104.0으로 고정합니다. `frontend/app/providers.tsx`는 `"use client"` `AppProviders` component로, `useState`로 browser session당 `QueryClient` 하나를 만들고 `QueryClientProvider`만 render합니다. Devtools, Redux, Zustand, SWR, axios는 없고 별도 client 전역 상태 store도 없습니다. *(이후: QueryClient 기본 `retry` 정책이 추가되었습니다. Client Query Retry Policy 참고.)*
- **Client/server boundary (ADR-008):** `app/layout.tsx`는 Server Component로 남아 `children`을 `AppProviders`로 감쌉니다. page는 기본적으로 Server Component이며, client provider로 감싸도 client component가 되지 않습니다. 당시 계획은 requester별 product data를 P4–P6의 좁은 client feature boundary에서 가져와 browser가 `/dev-user` cookie를 보내게 하는 것이었고, server 측 cookie 전달 API layer는 두지 않았습니다. *(이후: `lib/api/server.ts`가 home 목록 첫 page에 한해 requester만 전달합니다. First Page SSR 반영 참고.)*
- **공용 API client:** `frontend/lib/api/client.ts`의 `request()`가 유일한 fetch 진입점입니다. `NEXT_PUBLIC_API_BASE_URL`을 읽고(fallback `http://localhost:8080/api`, Compose build arg와 동일), path를 잇고, `URLSearchParams`로 query string을 encode합니다. 항상 `credentials: "include"`와 `cache: "no-store"`를 보내고, body가 있을 때만 `Content-Type: application/json`을 설정합니다. 204는 parse하지 않고 `undefined`를 반환하며, backend `{ code, message }` body로 `ApiError { status, code, message }`를 throw하고 fallback으로 `HTTP_ERROR` / `NETWORK_ERROR` / `INVALID_RESPONSE`를 씁니다.
- **Transport type:** `frontend/lib/api/types.ts`는 backend의 `PostResponse`, `CommentResponse`, `PageResponse`, `LikeToggleResponse`, `PostMutationRequest`, `CommentCreateRequest`, `ApiErrorResponse` field 이름을 그대로 따릅니다. API 경계에서 timestamp는 ISO 문자열로 유지합니다.
- **Endpoint 함수:** `frontend/lib/api/community.ts`에 과제 endpoint 9개를 모두 정의했습니다. feature hook(`useQuery`/`useMutation`)과 invalidation 정책은 cache 요구가 구체화되는 P4–P6로 미뤘습니다.
- **Query key:** `frontend/lib/query/keys.ts`의 `postKeys`는 안정적이고 직렬화 가능한 값(문자열 segment, 숫자 post ID, `{ limit: params.limit ?? null }` object)만 씁니다. infinite query가 cursor를 `pageParam`으로 다루므로 `cursor`는 key에서 뺐습니다. 변경 가능하거나 비결정적인 값은 key에 넣지 않습니다. *(이후: 목록 key에 sort와 검색어가 추가되었습니다. Post Discovery 반영 참고.)*
- **Route 계약 (`PRODUCT_DECISION`):** `/` 목록, `/posts/{postId}` 상세, `/posts/new` 작성, `/posts/{postId}/edit` 수정, `/dev-user` starter page이며 `frontend/lib/routes.ts`로 노출합니다. route page 자체는 P4–P6에서 구현했습니다.
- **Relative time (ADR-011):** threshold는 60초 미만 초, 60분 미만 분, 24시간 미만 시간, 30일 미만 일, 365일 미만 월, 그 이상 년입니다. 미래 시각은 `… 후`로, parse할 수 없는 입력은 `null`로 처리합니다. 당시에는 P4에서 client component가 현재 clock 기준으로 render할 때 server/client hydration 차이를 고려해야 한다고 적어 두었습니다.
- **Styling (ADR-009):** `globals.css`는 reset/font/base와 `docs/UI_SPEC.md`의 `DESIGN_DEFINED` token 일부(surface, primary/secondary/support text, light border, disabled surface, liked accent, scrim, toast surface, 16px page inset)를 가집니다. 점검한 값 외의 token은 만들지 않았습니다.

# Post Discovery 반영 (검색 + 정렬) — 2026-09-30

과제 범위를 넘는 `PRODUCT_DECISION`입니다. 목록을 검색하고 좋아요순으로 정렬할 수 있습니다. 새 parameter가 없으면 원래 계약은 그대로입니다.

**API — `GET /api/posts`**

| Param | 규칙 |
| --- | --- |
| `limit` | 1–50, 기본 20(변경 없음); 그 외 400 `INVALID_LIMIT` |
| `cursor` | Opaque; 같은 `sort`의 page에서 받은 값이어야 하며, 아니면 400 `INVALID_CURSOR` |
| `sort` | `latest`(기본) 또는 `likes`; 그 외 400 `INVALID_SORT` |
| `q` | trim 처리; 비어 있으면 검색 없음; 최대 100 code point, 넘으면 400 `INVALID_QUERY` |

응답은 계속 `{ items, total, nextCursor }`이며, `total`은 `q`에 맞는 읽을 수 있는 post 수입니다. `GET /api/posts?limit=10`은 `?limit=10&sort=latest`와 같습니다.

**정렬과 cursor**

- **latest:** `created_at DESC, id DESC`. 기존 `(created_at, id)` row-value keyset과 기존 `CursorCodec`을 그대로 씁니다. latest cursor는 이전과 byte 단위로 같습니다.
- **likes:** `effective_like_count DESC, created_at DESC, id DESC`이며 `effective_like_count = base_like_count + post_likes rows`입니다. keyset은 `(like_count, created_at, id) < cursor`입니다.
  - cursor는 `PostLikeCursorCodec`이 만드는 tag 붙은 `base64url("likes|count|createdAt|id")`이므로, 두 정렬은 서로의 cursor를 읽을 수 없습니다.
  - OFFSET은 쓰지 않습니다.
- 댓글 pagination(`PageRequestParser`, `CursorCodec`)은 그대로이며, 공통 limit 확인만 `parseLimit`으로 추출했습니다.

**검색**

- 제목이나 본문에 대한 대소문자 무시 부분 문자열 일치: `ILIKE :pattern ESCAPE '\'`.
- 사용자 입력은 bound parameter입니다. `\`, `%`, `_`를 escape하므로(`PostRepository.containsPattern`) `100%`나 `a_b`가 문자 그대로 일치합니다.
- 작성자는 검색하지 않고, soft delete된 post는 절대 일치하지 않습니다.

**SQL 형태.** 각 page는 page 자체(limit + 1행)와 filter된 `COUNT(*)`, 두 statement입니다. post마다 왕복하는 query는 없습니다.

- **latest:** 기존 query에 검색 조건만 더했습니다. 좋아요 수, 댓글 수, requester 좋아요는 `LIMIT` 뒤 반환된 row마다 correlated로 계산합니다.
- **likes:** 단일 statement입니다. `like_counts` CTE가 `post_likes`에 `GROUP BY`를 한 번 실행하고 읽을 수 있는 post를 여기에 join합니다. 그다음 검색과 keyset을 적용하고 `ORDER BY`와 `LIMIT`으로 `page` CTE를 만듭니다. 댓글 수와 requester 좋아요는 page row에만 붙입니다. `EXPLAIN ANALYZE`에서 11행 page에 대해 comment subplan은 `loops=11`이었습니다.
- **Index:** 추가하지 않았습니다. `ILIKE '%q%'`는 B-tree index를 쓸 수 없습니다. 이 dataset에서는 `pg_trgm`, migration, extension을 정당화할 수 없고, likes 정렬은 어차피 계산된 count가 필요합니다.

**알려진 한계 — 실시간 좋아요 수.** 데이터가 고정되어 있으면 likes 정렬은 결정적이고 page 사이에 중복·누락이 없습니다. 하지만 좋아요 snapshot은 없습니다. page 요청 사이에 다른 requester가 좋아요를 누르거나 취소하면 post가 cursor 경계를 넘을 수 있습니다.

- 두 page에 나타날 수 있습니다(frontend는 순서를 바꾸지 않고 post ID별로 한 번만 render합니다).
- 또는 목록을 다시 가져올 때까지 빠질 수 있습니다.

requester 본인의 좋아요는 likes 정렬 목록을 다시 가져오게 합니다(아래). 과거 snapshot은 이 과제에서 만들지 않았습니다.

**Frontend**

- **Query key:** `postKeys.list({ limit, sort, query })`는 `["posts","list",{ limit, sort, query }]`가 되며 `query`는 trim된 값 또는 `null`입니다. cursor는 `pageParam`이므로 sort/검색 조합마다 page 1에서 시작하는 별도 infinite query가 되고, cursor가 다른 목록으로 넘어가지 않습니다.
- **취소:** `getPosts(params, signal)`은 React Query의 `AbortSignal`을 `fetch`에 전달합니다. 대체되거나 unmount된 read는 취소되고, `request()`는 abort를 그대로 다시 throw하므로 `NETWORK_ERROR`가 되지 않습니다. *(이후 `getPost`와 `getComments`로 확장했습니다. "최종 ADR 상태" 참고.)*
- **검색 입력:** `searchInput`은 keystroke마다 갱신됩니다. 확정된 `query`는 300 ms debounce 뒤, 또는 Enter·지우기·닫기 시 즉시 따라갑니다.
- **Scroll reset:** sort나 검색이 바뀌면 sticky toolbar가 고정된 상태일 때 toolbar 아래로 scroll을 되돌립니다.
- **기억하는 view:** `lib/postListView.ts`는 앱 내 뒤로 가기를 위해 마지막 sort/검색을 `lib/flash.ts`처럼 module memory로 보관합니다.

**Cache matrix** (`lib/query/postListCache.ts`; 목록은 더 이상 하나의 공유 collection이 아닙니다):

| Mutation | 직접 수정 (정확히 아는 경우) | Invalidate (표시될 때 page 1부터 다시 가져옴) |
| --- | --- | --- |
| 글 생성 | filter 없는 latest 목록에만 맨 앞에 추가하고 `total + 1` | 그 외 모든 목록(검색 일치 여부나 likes 위치를 알 수 없음) |
| 글 수정 | 로드된 복사본을 모든 곳에서 교체; 순서는 그대로 | 검색 목록(본문이 바뀌면 membership이 바뀔 수 있음) |
| 글 삭제 | 모든 곳에서 row 제거; filter 없는 목록과 row가 로드된 곳에서 `total − 1` | 검색 목록(로드되지 않은 곳의 total이나 membership) |
| 좋아요 toggle | 모든 곳의 로드된 복사본에서 `isLiked`/`likeCount` | likes 정렬 목록(순서가 바뀔 수 있음) |
| 댓글 생성/삭제 | 모든 곳의 로드된 복사본에서 `commentCount` | 없음(정렬과 검색 membership에 영향 없음) |

# Deletion Consistency Model

post, comment, like를 하나의 model로 다룹니다. backend나 schema를 바꾸지 않은 상태에서 실행 중인 backend와 PostgreSQL로 검증했습니다(`docs/VERIFICATION.md` "Deletion Consistency Evidence").

**1. 물리적 보존.** post와 comment는 soft delete(`is_deleted = TRUE`)하며 row를 지우지 않습니다. post 삭제는 cascade하지 않습니다. 그 댓글은 자신의 `is_deleted` 값을 유지하고 `post_likes` row도 남습니다. 댓글은 작성자 본인의 삭제로만 삭제 상태가 됩니다.

**2. 가시성.**

```text
post readable    = NOT post.is_deleted
comment readable = NOT comment.is_deleted AND parent post readable
like effective   = parent post readable AND post_likes row exists
```

삭제된 post의 하위 데이터는 휴면 상태입니다. database에는 있지만 어떤 product API도 닿지 않습니다.

**3. API 의미.** 읽을 수 있는지를 ownership보다 먼저 확인합니다.

| 상태 | 결과 |
| --- | --- |
| 읽을 수 있는 resource + 소유자 | mutation 허용(`204` / `200` / `201`) |
| 읽을 수 있는 resource + 비소유자 | `403` |
| soft delete되었거나 존재한 적 없는 resource | `404` |
| parent post가 삭제된 댓글 | `404` |
| 반복 DELETE | 처음 `204`, 이후 `404`(idempotent-204 아님) |

따라서 삭제된 resource가 `403`을 통해 존재 사실을 드러내는 일은 없습니다.

**4. Parent 삭제.** post가 삭제되면 그 아래의 모든 route가 소유자·비소유자 모두에게 `404`를 반환합니다. GET/PATCH/DELETE, 좋아요 toggle, 댓글 목록, 댓글 생성, 기존 댓글 삭제가 모두 해당합니다. `PostReadService.getComments`는 먼저 `existsReadable`을 확인하고, `CommentRepository.findReadableMutationTargetForUpdate`는 읽을 수 있는 parent와 join합니다.

**5. Mutation 직렬화.** post 수정·삭제·좋아요 toggle과 댓글 생성은 각각 읽을 수 있는 post를 잠급니다(`SELECT … FOR UPDATE`, `is_deleted = FALSE`). 댓글 삭제는 읽을 수 있는 댓글과 읽을 수 있는 parent를 함께 잠급니다(`FOR UPDATE OF p, c`). 따라서 post 삭제와 하위 mutation이 경합하면 직렬화됩니다. 하위 mutation이 먼저 commit되어 휴면 상태가 되거나, 삭제 뒤에 실행되어 읽을 수 있는 parent를 찾지 못하고 `404`를 반환합니다. 15회 동시성 smoke test(삭제와 댓글 생성, 좋아요 toggle, 수정, 댓글 삭제의 경합)에서는 이 두 결과만 나왔고 5xx는 없었습니다.

**6. Frontend 일관성.** 서버가 확인하기 전에는 아무것도 바뀌지 않습니다. `204` 이후에는 다음과 같이 처리합니다.
- 모든 cached post-list query(당시에는 page size만 다른 같은 읽기 가능 collection)에서 삭제된 post가 로드된 page에 있든 없든 `total − 1`을 적용합니다. row가 로드된 곳에서는 row를 제거합니다. *(검색 목록에 대해서는 Post Discovery 반영으로 대체: 이제 목록이 sort와 검색으로 나뉘므로 그 cache matrix를 따릅니다.)*
- 삭제된 post의 detail query와 하위 comment query는 상세 화면이 unmount된 뒤 제거합니다. TanStack의 부분 key 일치로 `["posts","detail",id]`가 `[…,"comments",…]`까지 포함합니다.
- 이동은 `router.replace("/")`를 쓰므로 뒤로 가기로 삭제된 상세에 돌아가지 않습니다.
- keyset cursor는 `(createdAt, id)` 경계이므로, 삭제된 row가 cursor row였던 경우에도 유효합니다.

- **삭제 시 cache 반영:** 해당 댓글을 가진 page에서 제거하고 `total`을 1 내립니다. 삭제된 row를 가리키던 cursor도 다음 page 경계로 올바르게 동작합니다. row-value 조건은 실제 row가 있을 필요가 없기 때문입니다. 첫 page만 로드된 상태(접힌 view)라면 그 page를 한 번(`limit=2`) 다시 가져와 댓글 두 개가 계속 보이게 합니다.
- **모든 곳에 같은 count:** 결과 `total`을 절댓값으로 `postKeys.detail(id).commentCount`와 그 post를 포함한 모든 cached `postKeys.lists()` page에 씁니다(P5A 좋아요 방식과 같음). 댓글 목록이 아직 로드되지 않았다면 detail 값을 기준으로 count를 움직이고 댓글 목록을 다시 가져옵니다.
- **중복 방지:** 좋아요와 마찬가지로 `isPending`은 한 tick 늦게 render되므로, 두 mutation 모두 in-flight ref를 씁니다. 같은 tick의 두 번 제출·확인은 요청 하나만 보냅니다.
- **유지:** 댓글 query의 `gcTime: 0`. mutation 뒤에도 방문 단위 더보기 gate가 유지되며, 재방문 회귀 test를 통과했습니다.

# P5A Post Detail 반영 — 2026-09-29

- **Route boundary:** `app/posts/[postId]/page.tsx`는 segment를 검증하고(양의 safe integer, 아니면 `null`) `features/post-detail/PostDetailScreen`을 render하는 얇은 Server Component입니다. requester별 데이터는 모두 browser에서 가져오며 ADR-008과 일치합니다.
- **Detail query:** `usePostDetail()`은 `postKeys.detail(id)`를 쓰고 `ApiError` 404를 retry하지 않으므로, 없거나 soft delete된 post는 바로 not-found 상태가 됩니다. *(이후: 404 전용 예외는 공통 4xx 규칙으로 대체되었습니다. Client Query Retry Policy 참고.)* `CommentSection`은 post가 로드된 뒤에만 mount되므로, 삭제된 post는 댓글 요청을 만들지 않습니다.
- **좋아요 동기화:** `useTogglePostLike()`는 의도적으로 non-optimistic입니다. 서버의 `{ isLiked, likeCount }`를 `setQueryData`로 detail cache에, `setQueriesData`로 그 post를 포함한 모든 cached `postKeys.lists()` infinite page에 써서, 목록으로 돌아가면 refetch를 기다리지 않고 같은 값을 보여 줍니다. *(이후: likes 정렬 목록은 invalidate됩니다. Post Discovery 반영의 cache matrix 참고.)* toggle이 실패하면 cache는 바뀌지 않습니다. in-flight `useRef` guard가 `isPending`이 render되기 전 tick의 두 번째 toggle을 막습니다. `/dev-user`는 full page load로 user를 바꾸고 이때 새 `QueryClient`가 만들어지므로, requester 분리를 위해 cache를 나눌 필요가 없습니다.
- **댓글 pagination:** `useComments()`는 `postKeys.commentList(id)`에 대한 `useInfiniteQuery` 하나이며 `pageParam`은 `{ cursor?, limit }`입니다. 첫 page는 `{ limit: 2 }`, 이후 page는 `{ cursor: nextCursor, limit: 20 }`입니다. *(이후 측정을 거쳐 `COMMENT_PAGE_SIZE = 30`으로 바꿨고, 고정 읽기 깊이로 다시 측정한 뒤 유지했습니다. Comment Continuation & Rendering Decision 참고.)* keyset cursor가 `(createdAt, id)`를 담으므로 page 사이에 page size가 바뀌어도 row가 빠지거나 중복되지 않습니다. backend 변경은 필요 없었습니다.
- **더보기 / 이어 읽기 gate:** `CommentSection`은 방문 단위 `expanded` flag를 가집니다. 접힌 상태에서는 첫 page의 최대 두 개만 render하고 `total >= 3`일 때만 더보기를 보여 줍니다. 더보기는 `expanded`를 켜고 `fetchNextPage()`를 한 번 호출합니다. 공용 `useInfiniteScrollTrigger`(ADR-010)는 `expanded && hasNextPage && !isFetchingNextPage && !isFetchNextPageError`일 때만 활성화되므로, sentinel이 보여도 더보기 전에는 가져오지 않습니다. P4와 마찬가지로 이어 읽기 실패도 `status: "error"`를 설정하므로, 초기 오류 block은 `data === undefined`를 요구합니다.
- **방문 단위 댓글 cache:** `useComments()`는 `gcTime: 0`을 설정해, 상세 화면이 unmount되는 즉시 댓글 query와 이어 읽은 page를 제거합니다. 이것이 없으면 page가 공유 `QueryClient`에 남았습니다. 같은 session에서 재방문하면 stale mount refetch가 더보기 전에 cached 이어 읽기 page를 모두 다시 요청했고, 더보기를 누르면 cached 댓글이 한꺼번에 드러났습니다. 이제 방문마다 `limit=2` page 하나로 시작합니다. 비용은 방문당 `limit=2` 요청 하나와 즉시 보이는 cached 댓글이 없다는 점입니다. `refetchOnMount: false`만으로는 cached page가 더보기 시 한꺼번에 나타나므로 제외했습니다.

# First Page SSR 반영 — 2026-10-02

- **이유:** 목록의 LCP는 HTML → JS/hydration → browser `GET /posts` → render를 기다렸습니다. API 자체는 빨랐지만 hydration 전에는 요청을 시작할 수 없었습니다. 첫 page를 server에서 가져오면 이 연쇄가 사라집니다(devtools throttling Lighthouse, Docker: LCP median ≈3.47s → ≈2.36s; 로드 시 browser `GET /posts` 1 → 0).
- **범위:** 기본 view(`latest`, 검색 없음, `limit` 15)의 첫 page만입니다. 이후 page(`nextCursor`), likes 정렬, 검색은 계속 client React Query 요청이며 routing과 URL은 바뀌지 않습니다.
- **Server read:** `app/page.tsx`가 `x-user-id` cookie를 읽고 `lib/api/server.ts`(`server-only`)를 호출합니다. `API_BASE_URL`(Compose: `http://backend:8080/api`)을 쓰고, requester는 `x-user-id` header로만 보냅니다(backend가 cookie에서 읽을 값과 같도록 다시 encode하며, cookie가 없으면 생략해 backend 기본값을 따름). `cache: "no-store"`와 2.0s timeout을 씁니다. 실패하면 모두 `null`을 반환합니다. page는 그대로 render되고 기존 client fetch / error / retry 경로가 실행됩니다.
- **Client seed:** `usePostList`는 바뀌지 않은 key `["posts","list",{limit:15,sort:"latest",query:null}]` 아래에 그 page를 `initialData`(`pages: [page]`, `pageParams: [undefined]`)로 넘깁니다. `initialData`는 기존 cache entry를 덮어쓰지 않으므로, 기억된 sort/검색 view와 뒤로 가기는 이전처럼 동작합니다. `staleTime`은 `dataUpdateCount === 0`(seed)일 때만 5s이므로 hydration 시 refetch를 막고, client fetch가 한 번이라도 일어나면 다시 0입니다.
- **Relative time:** server render와 hydration render는 server의 `fetchedAt`을 `now`로 쓰고, mount 뒤에는 실시간 clock을 씁니다.
- **Trade-off:** `/`는 이제 dynamic route입니다(cookie와 최신 데이터를 읽음). TTFB에 내부 fetch가 포함됩니다(≈30–50ms, backend가 멈추면 최대 2.0s).

## SSR Freshness와 Failure Budget — 2026-10-03

두 값은 의도적으로 책임이 다르며 따로 조정합니다.

- **Seed freshness (`SEED_FRESH_MS = 5_000`):** React Query는 관찰된 hydration 구간 동안 SSR 첫 page cache entry를 fresh로 취급해 server가 한 일을 반복하지 않습니다. throttling을 건 hard load 5회에서 seed 나이는 약 1.65 s였고, 5/15/30초에서는 중복 요청이 없었으며 0초에서는 5회 모두 중복되었습니다. 5초는 성공한 후보 중 가장 짧은 값입니다. freshness는 polling이 아닙니다. stale query가 focus, remount, 명시적 invalidation 같은 일반 trigger의 대상이 될 수 있게 할 뿐입니다.
- **Server blocking (`SERVER_FETCH_TIMEOUT_MS = 2_000`):** SSR이 upstream을 기다리는 시간의 상한입니다. server에만 1.8초 지연을 걸었을 때 2초에서는 SSR content를 유지해 실제 post LCP median이 2.98 s였고, 1.5초에서는 CSR로 fallback되어 4.04 s였습니다. blackhole은 fallback 실제 post LCP에 0.54 s를 더합니다(4.05 → 4.59 s). 측정된 느린 SSR 이득을 유지하는 대가로 수용한, 범위가 정해진 실패 비용입니다.
- **실패 경로:** timeout은 server retry 없이 `null`을 반환하고, page는 HTTP 200으로 응답한 뒤 client 목록을 hydrate합니다. 그 browser fallback은 별도로 분류된 query retry 정책을 따릅니다(4xx 없음; network/5xx/알 수 없는 오류 1회). 두 budget을 묶어서는 안 됩니다.

# List Batch Size Decision — 2026-10-02

근거: `docs/PERFORMANCE.md` §13(일회용 160-post dataset, 375×778, CPU 4×, Lighthouse devtools mobile throttling, 고정 소비 깊이 30·45 post).

- **분리된 parameter:** first-page SSR이 있으면 server render page 크기(`SSR_SIZE`)와 이후 각 cursor 요청 크기(`CONTINUATION_SIZE`)는 독립된 결정입니다. 각각 첫 render와 scroll에 영향을 주므로 따로 측정했습니다(각 10/15/20).
- **결정 — 15/15 유지:** SSR 10/15/20의 LCP 차이는 측정 noise 범위 안이었습니다. 이어 읽기 10은 요청이 늘고 읽는 속도에서도 loading 문구가 보였으며, 20은 15보다 일관된 이득이 없었습니다. 크기를 다르게 해서 얻는 측정된 이득이 없어 둘 다 `POST_LIST_PAGE_SIZE = 15`로 둡니다. 이 조건에서 비교한 후보 중 가장 합리적인 값이지 보편적 최적값은 아니며, seed의 읽을 수 있는 post 39개를 세 번의 요청으로 나누려고 고른 값도 아닙니다.
- **전체 개수에서 크기를 끌어내지 않는 이유:** 전체 post 수와 한 사용자의 소비 깊이는 다른 양입니다. cursor pagination은 사용자가 scroll한 만큼만 요청하므로(요청당 `limit + 1`행), post가 42개든 1,000개든 100,000개든 page size를 키울 이유가 없습니다. 전체 개수는 끝까지 읽는 사람에게만 의미가 있습니다. 고정 깊이 비교가 맞는 기준입니다.
- **혼합 크기 비용 (채택하지 않음):** 15/20 같은 조합도 가능하지만, 그러면 key의 `limit`이 모든 page를 설명하지 못하고, 첫 page와 이후 page의 크기가 달라지며, SSR 실패 시 client fetch와 refetch/invalidation 경로에 첫 page 분기가 필요하고, cache test가 늘어납니다. 측정된 이득이 없어 채택하지 않았습니다.
- **남은 항목(당시):** benchmark는 빠른 scroll 중 대기가 page size보다 다음 page를 얼마나 일찍 요청하느냐에 더 좌우된다는 점을 시사했습니다. `rootMargin`(200px)은 측정할 후속 항목으로 남겼고 바꾸지 않았습니다. *(이후: 측정함. List Prefetch Distance Decision 참고.)*

# List Prefetch Distance Decision — 2026-10-02

근거: `docs/PERFORMANCE.md` §14(§13과 같은 조건; 200/300/400/500 px 비교).

- **분리된 parameter:** prefetch 거리(sentinel `rootMargin`)는 다음 page를 언제 요청할지를, page size는 얼마나 담을지를 정합니다. 요청부터 row 표시까지의 지연(throttling 기준 ≈0.66s)과 scroll 속도에 비추어 판단합니다. ≈600px/s로 훑으면 ≈400px, ≈300px/s면 ≈200px를 이동합니다.
- **결정 — post 목록 500px:** 200px에서는 빠르게 훑을 때 모든 page 경계에서 기다렸고(300px은 절반), 400px은 대기가 사라졌지만 빈 영역이 보였으며, 500px은 둘 다 없앴습니다. 어떤 후보도 scroll 전에 page를 요청하거나, 요청을 연쇄하거나, 일찍 떠날 때 더 많이 로드하지 않았습니다. 그래서 200px 대비 500px의 비용은 미리 가져오는 최대 한 page(15행)입니다. 이 조건에서 비교한 후보 중 가장 합리적인 값이지 일반적 최적값은 아닙니다.
- **범위:** `PostListScreen`이 `POST_LIST_PREFETCH_ROOT_MARGIN`을 명시적으로 넘깁니다. 댓글 이어 읽기가 hook을 공유하지만 측정하지 않았으므로 hook 기본값은 200px로 둡니다.
- **Trade-off:** 높이가 약 1,212px 이상인 viewport(측정하지 않음)에서는 첫 page의 sentinel이 이미 500px margin 안에 있어, scroll 전에 page 2를 한 번 요청하게 됩니다.

# Client Query Retry Policy — 2026-10-03

- **결정:** 모든 client read는 `frontend/lib/query/retryPolicy.ts`의 QueryClient 기본값 `retryOnceUnlessDeterministicClientError`를 씁니다. 개별 query hook은 retry 정책을 중복 정의하지 않습니다.
- **분류:** 완료된 `ApiError` 4xx 응답은 첫 실패에서 `false`를 반환합니다. network 오류(`ApiError` status 0), 5xx 응답, 알 수 없는 query 실패는 `failureCount < 1`을 반환합니다. TanStack Query가 처음 실패한 시도에 대해 0으로 predicate를 호출하므로, 이는 정확히 한 번의 retry입니다.
- **이유:** 설치된 v5.104.0 runtime의 이전 기본값은 1 s, 2 s, 4 s 지연으로 네 번 시도했습니다. 영구적인 read 실패라면 UI가 기존 수동 retry를 보여 주기까지 약 7초를 기다렸습니다. retry 한 번이면 관찰된 1회 실패 자동 복구를 약 1초 만에 유지합니다. 기본 지연을 product 전용 값으로 바꾸지는 않았습니다.
- **404와 UI:** 없거나 soft delete된 post는 이제 공통 4xx 규칙을 따르므로, `usePostDetail`이 404 전용 예외를 갖지 않습니다. not-found UI는 계속 즉시 표시됩니다. 목록/댓글 이어 읽기 page는 최종 실패 후에도 로드된 데이터를 유지하고 기존의 명시적 retry를 요구합니다.
- **취소:** read query 함수는 계속 받은 `AbortSignal`을 `fetch`에 전달하고, `request()`는 abort된 오류를 그대로 다시 throw합니다. TanStack Query의 취소는 정책이 다음 시도를 예약하기 전에 retryer를 멈추므로, error UI도 stale 덮어쓰기도 생기지 않습니다.
- **Mutation 경계:** 어떤 mutation도 `retry`를 지정하지 않으므로 TanStack Query mutation 기본값인 자동 retry 0회가 유지됩니다. 좋아요 toggle, post 생성/수정/삭제, 댓글 생성/삭제는 non-optimistic이며 서버 확인 후 반영됩니다.
- **별도의 SSR budget:** browser retry 정책은 `SERVER_FETCH_TIMEOUT_MS`, SSR fallback, seed `staleTime`을 바꾸지 않습니다. server render 실패 처리는 별개의 budget입니다.

# Data Read Architecture — 결정 근거

이 section은 read 경로가 왜 지금 모양인지 설명합니다. 어떤 조건에서 만들었는지, 성능 점검(`docs/PERFORMANCE.md`)이 무엇을 측정했는지, 측정이 정당화한 단 하나의 변경이 무엇인지를 다룹니다.

## 1. 출발 조건

일반적인 확장성 고민보다 제공된 seed가 model을 더 많이 결정했습니다.

- post 42개(3개 soft delete)와 comment 2,076개(81개 soft delete). 삭제 여부는 `deletedPostIds` / `deletedCommentIds`로 주어집니다.
- post는 `likeCount`를 갖지만 **user별 좋아요 이력은 없습니다**.
- **`commentCount` field가 없습니다.** 과제는 삭제된 댓글을 제외하고 댓글에서 파생하도록 요구합니다.
- 모든 post와 comment는 ISO `createdAt`과 고유 `id`를 가지므로 `(createdAt, id)`가 전체적이고 안정적인 순서를 줍니다. seed에는 같은 timestamp가 없지만, 순서는 그 사실에 의존하지 않습니다.

첫 구현의 목표는 다음과 같았습니다.

- database를 유일한 원본으로 두고, 파생 숫자의 두 번째 복사본을 두지 않는다.
- 생성/삭제 뒤 count와 row가 어긋날 수 없게 한다.
- soft delete를 목록, 상세, count, mutation에 똑같이 적용한다.
- infinite scroll의 요청마다 read 범위를 제한한다.
- 과제 규모에 필요 없는 비정규화나 cache layer를 피한다.

## 2. `commentCount`를 저장하지 않고 계산하는 이유

`commentCount`와 댓글 `total`은 read 시점에 계산합니다.

```sql
SELECT COUNT(*) FROM comments WHERE post_id = ? AND is_deleted = FALSE
```

`posts.comment_count` column은 없습니다.

- seed에 그런 column의 원본 값이 없어서 어차피 파생해야 합니다.
- 저장된 counter는 모든 mutation transaction 안에서 댓글 생성, soft delete, post 삭제와 함께 맞춰야 합니다. 한 경로라도 빠지면 어긋나고, 그러면 `DEL-006`, `SEED-008`, `SEED-009`가 깨집니다.
- 계산된 count를 쓰면 comments table이 유일한 원본으로 남고 mutation transaction도 단순해집니다.

점검 결과도 이 선택을 뒷받침했습니다. 최악인 post #2(읽을 수 있는 댓글 1,411개)에서 COUNT는 warm 상태로 ≈0.39 ms입니다. API 수준에서 댓글 2개짜리 post와 post #2의 댓글 page latency는 같았습니다(median 6.61 vs 7.28 ms). **정규화된 model을 유지하며, `posts.comment_count`는 추가하지 않습니다.**

## 3. 좋아요를 `base_like_count` + `post_likes`로 두는 이유

seed는 post의 좋아요 수는 알려 주지만 누가 눌렀는지는 알려 주지 않습니다. 이 model은 데이터를 지어내지 않고 두 사실을 모두 보존합니다.

- seed 숫자는 `posts.base_like_count`에 저장하고 바꾸지 않습니다.
- application 실행 중 생긴 좋아요는 `post_likes (post_id, user_id)` row입니다. primary key가 중복 좋아요를 막습니다.
- `likeCount = base_like_count + COUNT(post_likes rows)`이고, `isLiked`는 requester에 대한 `EXISTS`입니다.

seed 값을 정확히 보존하고, requester별 `isLiked`를 지원하며, user별 seed 이력을 지어내지 않습니다(ADR-005 참고).

## 4. OFFSET 대신 keyset pagination을 쓰는 이유

두 collection 모두 `ORDER BY created_at DESC, id DESC`로 정렬하고, 마지막 `(createdAt, id)`를 담은 cursor에서 이어갑니다(ADR-006). 의도는 다음과 같았습니다.

- `id`가 같은 timestamp를 구분하는 안정적인 순서.
- scroll 중 새 row가 들어와도 page가 밀리지 않음.
- 깊어질수록 늘어나는 OFFSET식 작업이 없어 댓글 infinite scroll에 맞음.

keyset 계약은 논리적으로는 올바르게 구현했습니다. **하지만 cursor 조건이 실제로 index scan 범위를 제한하는지는 성능 점검 전까지 PostgreSQL 실행 계획으로 확인하지 않았습니다.**

## 5. 성능 점검을 한 이유

seed 분포를 다시 계산하니 극단적으로 치우쳐 있었습니다.

- 읽을 수 있는 post의 읽을 수 있는 댓글 1,926개; post당 median 7, 평균 ≈49.4, 최대 1,411.
- post #2 하나가 읽을 수 있는 댓글의 ≈73.3 %를, 상위 5개 post가 ≈83.2 %를 가집니다.

따라서 제공된 seed에는 크고 치우친 workload가 들어 있었고, 이를 stress fixture로 썼습니다. 직감으로 최적화하지 않고 clean seed 비용, API latency, 요청당 SQL statement 수, 얕은·깊은 cursor에서의 `EXPLAIN (ANALYZE, BUFFERS)`, post #2 전체 순회를 측정했습니다(`docs/PERFORMANCE.md`).

## 6. 그대로 두는 것

측정 후 유지한 것:

- query 시점의 댓글 `COUNT`와 page별 `total`;
- 파생 좋아요 수와 requester `EXISTS`;
- soft delete model;
- 현재 composite index;
- 단일 transaction seed 초기화;
- 정규화된 comments model.

각각 1 ms 미만의 SQL이거나 제공된 seed에서 API latency의 의미 있는 부분이 아닙니다. 비정규화 counter, cache, 추가 index는 측정된 이득 없이 일관성 위험과 code만 늘립니다.

## 7. 점검이 정당화한 단 하나의 변경 — 적용함

cursor 조건은 원래 다음과 같았습니다.

```sql
created_at < :cursorCreatedAt
OR (created_at = :cursorCreatedAt AND id < :cursorId)
```

의미는 맞지만 PostgreSQL은 이를 `Index Cond: post_id = …` 뒤의 `Filter`로 적용했습니다. page마다 그 post의 index 범위를 가장 최신 row부터 훑었습니다. post #2에서 filter로 버려진 row는 3(첫 이어 읽기) → 728(중간) → 1,459(가장 깊은 page)로, buffer는 6 → 23 → 42로 늘었습니다. 계약상으로는 keyset이었지만 실행은 OFFSET처럼 동작했습니다.

read-only 실험에서 row-value 형태

```sql
(created_at, id) < (:cursorCreatedAt, :cursorId)
```

는 `Index Cond`의 일부가 되었습니다. 가장 깊은 page는 결과 집합이 같은 채로 3–4 buffer, ≈0.11 ms(이전 ≈0.29 ms)로 줄었습니다.

이 변경은 `b86f668`에서 `PostRepository.findReadablePage`와 `CommentRepository.findReadablePage`에 적용했고 다른 것은 바꾸지 않았습니다. 두 column이 모두 `NOT NULL`이고, 두 정렬 모두 `created_at DESC, id DESC`이며, cursor가 정확히 `(createdAt, id)`이므로 유효합니다. 이유는 절약한 1 ms 미만의 시간이 아닙니다. page 깊이에 따라 늘던 scan 작업이 거의 일정한 비용의 index seek가 된다는 점이고, 이것이 keyset pagination을 고른 이유였습니다.

변경 후 다시 측정했습니다. post #2에서 row-value 경계가 `Index Cond`에 나타나고, buffer는 첫 이어 읽기부터 마지막 page까지 3–4로 유지됩니다(이전: 6 → 23 → 42, 최대 1,459 row filter). page 경계가 같은 timestamp 묶음 안에 걸리는 tie fixture를 포함해 모든 순회가 변경 전후 같은 결과를 반환했습니다. 이 규모에서 API latency는 측정 가능한 수준으로 바뀌지 않았고, 요청당 statement 수도 그대로입니다(`docs/PERFORMANCE.md` §12).

# ADR-001 — Persistence Access: Spring JDBC `JdbcClient`, not JPA

**상태:** `DECIDED`

## 결정

Spring JDBC의 `JdbcClient`와 명시적 SQL repository를 씁니다. P0에서 data model을 크게 바꿀 만한 강한 요구가 드러나지 않는 한 JPA/Hibernate를 추가하지 않습니다. *(P0에서 그런 요구는 없었고 JPA는 추가하지 않았습니다. Repository: `backend/.../persistence/`.)*

## 근거

- Starter evidence: 제공 README는 `spring-boot-starter-jdbc`가 이미 포함되어 있고 persistence 기술은 지원자에게 맡긴다고 설명합니다.
- Spring Framework 6.2 문서는 application code가 SQL을 맡고, Spring JDBC가 connection/resource lifecycle, exception 변환, transaction 참여를 처리한다고 설명합니다.
  - https://docs.spring.io/spring-framework/reference/6.2/data-access/jdbc.html
- Spring Framework 6.2는 일반적인 JDBC query/update 작업을 위한 fluent facade로 `JdbcClient`를 제공합니다.
  - https://docs.spring.io/spring-framework/reference/6.2/data-access/jdbc/core.html

## 선택 이유

domain은 의도적으로 작습니다. post, comment, requester별 좋아요, seed metadata뿐입니다. 어려운 부분은 object graph 영속화가 아니라 명시적인 query 의미입니다.

- 최신순 pagination,
- requester별 `isLiked`,
- 파생 `commentCount`,
- soft delete filter,
- ownership 확인,
- 정확한 API 응답 형태.

명시적 SQL은 이 규칙을 code에 그대로 드러내고, 과제에 필요 없는 entity lifecycle, lazy loading, dirty checking, ORM mapping 동작을 더하지 않습니다.

## 검토한 대안

### Spring Data JPA / Hibernate

장점:
- CRUD boilerplate가 적음,
- 익숙한 repository/entity model,
- 자동 변경 추적.

선택하지 않은 이유:
- 과제의 table 수가 적고 풍부한 aggregate graph가 없음,
- 중요한 read는 어차피 custom query 설계가 필요함,
- 설명하고 test해야 할 추상화 범위가 커짐.

## 수용한 비용

SQL과 mapping code를 더 많이 직접 씁니다. 대신 database 동작이 명시적이고 바로 검토할 수 있습니다.

# ADR-002 — Schema Management: Flyway for schema, application code for assignment seed

**상태:** `DECIDED` — 구현 완료. P0 당시에는 Flyway가 선언되지 않아 `OPEN`이었습니다.

## 결정

schema 변화에는 Flyway의 versioned SQL migration을 씁니다. schema 생성에 Flyway와 `schema.sql`/`data.sql`을 섞지 않습니다.

`seed/seed.json`은 schema가 생긴 뒤 application 기동 logic으로 로드합니다. 과제가 제공한 JSON을 숨겨진 SQL 복사본으로 바꾸지 않습니다.

## 구현

- `backend/build.gradle`이 `org.flywaydb:flyway-database-postgresql`을 선언합니다. Spring Boot가 기동 시 migration을 실행합니다.
- migration은 `backend/src/main/resources/db/migration/V1__create_community_schema.sql` 하나뿐이며, `schema.sql`이나 `data.sql`은 없습니다.
- seed는 migration이 아니라 `SeedInitializer`(ADR-013)가 로드합니다.

## 근거

- Spring Boot 3.5는 schema 초기화 방식을 하나만 쓰도록 권장하고 Flyway 통합을 설명합니다.
  - https://docs.spring.io/spring-boot/3.5/how-to/data-initialization.html
- 같은 Spring Boot 문서는 PostgreSQL에 database 전용 Flyway module이 필요하고, migration은 관례상 `classpath:db/migration`에 둔다고 설명합니다.
  - https://docs.spring.io/spring-boot/3.5/how-to/data-initialization.html
- Flyway는 versioned migration이 순서대로 한 번만 적용되고 checksum과 함께 schema 이력에 기록된다고 설명합니다.
  - https://documentation.red-gate.com/fd/versioned-migrations-273973333.html

## 선택 이유

평가자는 repository를 clone한 뒤 `docker compose up`으로 같은 schema를 얻을 수 있어야 합니다. versioned SQL migration은 schema를 명시적이고 검토 가능하며 재현 가능하게 만듭니다.

과제는 `seed/seed.json`을 초기 데이터의 원본으로 명시합니다. seed parsing을 application code에 두면 같은 데이터의 두 번째 복사본을 SQL로 관리하지 않고 그 원본을 그대로 지킬 수 있습니다.

## 수용한 비용

Flyway는 dependency 하나와 migration 관례를 더합니다. schema 생성이 결정적이고 점검 가능해지므로 감수할 만한 비용입니다.

# ADR-003 — IDs: PostgreSQL identity columns that also accept seed IDs

**상태:** `DECIDED` — 구현 완료. seed와 schema가 생기기 전까지는 `PROVISIONAL`이었습니다.

## 결정

post/comment ID에 `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`를 씁니다.

- seed import는 과제가 제공한 ID를 명시적으로 insert합니다.
- 새로 만드는 row는 ID를 생략하고 identity sequence를 씁니다.
- 첫 seed import 뒤, 생성 ID를 받기 전에 identity sequence를 import된 최대 ID 위로 맞춥니다.

## 구현

- `V1__create_community_schema.sql`은 `posts.id`와 `comments.id`를 `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`로 선언합니다.
- `PostRepository.insertSeedPost`와 `CommentRepository.insertSeedComment`는 seed ID를 명시적으로 insert합니다. product 생성은 ID를 생략합니다.
- `IdentitySequenceRepository.synchronizeWithSeededRows()`는 두 table에 대해 `setval(pg_get_serial_sequence(table, 'id'), MAX(id), true)`를 실행합니다. `SeedInitializer` transaction 안에서, `seed_history` marker를 쓰기 전에 실행됩니다.

## 근거

- Assignment evidence: seed ID는 정확히 보존해야 하고, 새 post/comment의 ID는 자유롭게 정할 수 있습니다.
- PostgreSQL 문서는 `GENERATED BY DEFAULT AS IDENTITY`가 사용자가 명시한 값을 받으면서도 ID를 생략하면 값을 생성한다고 설명합니다.
  - https://www.postgresql.org/docs/current/ddl-identity-columns.html
- PostgreSQL 문서는 identity column에 연결된 sequence를 얻는 `pg_get_serial_sequence`를 설명합니다.
  - https://www.postgresql.org/docs/current/functions-info.html
- PostgreSQL 문서는 sequence 값을 맞추는 `setval`을 설명합니다.
  - https://www.postgresql.org/docs/current/functions-sequence.html

## 선택 이유

application 안에 별도 ID 할당기를 두지 않고도 상충하는 두 요구를 모두 만족합니다.

1. import한 row는 원래 숫자 ID를 유지합니다.
2. product에서 만든 row는 생성된 숫자 ID를 받습니다.

## 위험과 해결

identity 값을 명시적으로 넣는다고 해서 그 뒤의 sequence가 그 값 위로 자동으로 올라가지는 않습니다. 위의 명시적 sequence 동기화는 이 때문입니다. seed ID는 정확히 보존되고, 처음 만든 post와 comment는 충돌 없는 ID를 받습니다(`SEED-005`–`SEED-007`, `docs/VERIFICATION.md` V-003).

# ADR-004 — Data Model and Soft Delete

**상태:** `DECIDED` — `V1__create_community_schema.sql`에 구현했습니다. P0 이전에는 `deleted_at` 기반 형태가 작업 제안이었고 `PROVISIONAL`이었습니다(아래 "변화" 참고).

## 결정

product table 3개와 seed metadata table 1개를 씁니다. 실제 반영된 schema입니다.

```sql
CREATE TABLE posts (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(20) NOT NULL,
    content TEXT NOT NULL,
    author TEXT NOT NULL,
    base_like_count INTEGER NOT NULL CHECK (base_like_count >= 0),
    created_at TIMESTAMPTZ NOT NULL,
    is_deleted BOOLEAN NOT NULL DEFAULT FALSE
);

CREATE TABLE comments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    post_id BIGINT NOT NULL REFERENCES posts (id),
    content TEXT NOT NULL,
    author TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    is_deleted BOOLEAN NOT NULL DEFAULT FALSE
);

CREATE TABLE post_likes (
    post_id BIGINT NOT NULL REFERENCES posts (id),
    user_id TEXT NOT NULL,
    PRIMARY KEY (post_id, user_id)
);

CREATE TABLE seed_history (
    seed_key VARCHAR(64) PRIMARY KEY,
    imported_at TIMESTAMPTZ NOT NULL
);

CREATE INDEX posts_created_at_id_idx ON posts (created_at DESC, id DESC);
CREATE INDEX comments_post_id_created_at_id_idx ON comments (post_id, created_at DESC, id DESC);
```

- `title VARCHAR(20)`: PostgreSQL은 문자 단위로 세므로 `MutationValidator`의 20 code point 규칙과 맞습니다.
- `author`와 `user_id`는 `TEXT`: requester 이름은 과제가 길이를 정하지 않은 header나 cookie에서 오므로 길이를 지어내지 않았습니다.
- user table은 없습니다. ownership은 `author == requester`입니다(ADR-012).

## 변화 — 초기 제안과 최종 schema

P0 이전 제안은 post와 comment에 `deleted_at TIMESTAMPTZ NULL`, `posts.updated_at`, `post_likes.created_at`, 임시 `VARCHAR(...)` 길이를 두었습니다. 최종 schema에서는 다음과 같이 바뀌었습니다.

| 초기 제안 | 최종 | 이유 |
| --- | --- | --- |
| `deleted_at TIMESTAMPTZ NULL` | `is_deleted BOOLEAN NOT NULL DEFAULT FALSE` | "`deleted_at` 대신 `is_deleted`를 쓰는 이유" 참고 |
| `posts.updated_at` | 없음 | 수정 시각을 읽는 API field나 동작이 없음 |
| `post_likes.created_at` | 없음 | 좋아요는 존재 여부와 개수로만 읽음 |
| `author VARCHAR(...)` | `author TEXT` | 강제할 길이 정의가 없음 |

## 근거

- Assignment evidence: 별도 user table은 필요 없고, ownership은 `author == requester`입니다.
- Assignment evidence: post/comment는 삭제 뒤에도 물리적으로 남되 일반 read에서는 사라져야 합니다.
- PostgreSQL 문서는 foreign key를 database 수준의 참조 무결성으로 설명합니다.
  - https://www.postgresql.org/docs/current/tutorial-fk.html
- PostgreSQL `timestamp with time zone`은 timestamp 값을 내부적으로 정규화하며, 과제의 ISO timestamp 같은 절대 시각에 적합합니다.
  - https://www.postgresql.org/docs/current/datatype-datetime.html

## Soft delete 규칙

일반적인 product 삭제는 다음과 같습니다.

```text
is_deleted: FALSE -> TRUE
```

`deletedPostIds` / `deletedCommentIds`에 있는 seed row는 `is_deleted = TRUE`로 insert합니다. 일반 목록/상세/count query는 `is_deleted = TRUE`를 없는 것으로 다룹니다(parent post가 그런 경우 댓글도 없는 것으로 다룹니다. "Deletion Consistency Model" 참고).

적용 대상:

- post 목록,
- post 상세,
- 댓글 목록,
- `commentCount`,
- mutation 대상.

## `deleted_at` 대신 `is_deleted`를 쓰는 이유

`deleted_at`은 삭제 시각까지 기록할 수 있어 초기 제안이었습니다. 실제 schema에서는 다음 이유로 제외했습니다.

- seed는 삭제 **여부**(`deletedPostIds`, `deletedCommentIds`)만 주고 삭제 **시각**은 주지 않습니다.
- import한 삭제 row에 `deleted_at`을 쓰려면 원본 데이터에 없는 timestamp를 지어내야 합니다. Architecture Review 확정은 seed 데이터로 만들어 낸 삭제 timestamp를 금지합니다.
- 언제 삭제되었는지 보여 주는 API field나 화면이 없습니다.

boolean은 알려진 사실만 정확히 기록합니다. 대신 runtime 삭제도 삭제 시각을 남기지 않는다는 비용을 수용했습니다. audit trail이 필요하면 별도 결정이 필요합니다.

## Index 정책

실제 read가 정당화하는 query 형태의 index만 둡니다.

```text
posts_created_at_id_idx            posts(created_at DESC, id DESC)
comments_post_id_created_at_id_idx comments(post_id, created_at DESC, id DESC)
```

추측성 index나 partial index는 추가하지 않았습니다. seed는 post 42개와 comment 2,076개뿐입니다. 성능 점검(`docs/PERFORMANCE.md`)은 이 두 index를 유지하고 cursor 조건만 바꿨습니다("Data Read Architecture" §7 참고). 나중에 query plan이 `is_deleted = FALSE` partial index를 정당화하면 그 근거와 함께 추가합니다.

PostgreSQL 문서:
- multicolumn indexes: https://www.postgresql.org/docs/current/indexes-multicolumn.html
- partial indexes: https://www.postgresql.org/docs/current/indexes-partial.html

# ADR-005 — Likes: Historical Base Count + Requester Like Rows

**상태:** `DECIDED`

## 결정

seed 좋아요와 requester 좋아요를 분리해 표현합니다.

```text
posts.base_like_count
post_likes(post_id, user_id)
```

API 응답:

```text
likeCount = base_like_count + count(post_likes for the post)
isLiked   = whether (post_id, current_user) exists in post_likes
```

## 근거

- Assignment evidence: seed 데이터에는 `likeCount`가 있지만 좋아요 이력은 없습니다.
- Assignment evidence: 따라서 모든 requester의 `isLiked`는 false로 시작합니다.
- Assignment evidence: 좋아요는 requester별 toggle이며, count는 toggle에 따라 바뀌어야 합니다.

## 선택 이유

seed count는 입력에 user 정보가 없는 과거 좋아요입니다. 그 좋아요에 user를 지어내면 데이터를 조작하는 셈입니다.

과거 count는 base 값으로 두고 이 application에서 만든 좋아요만 저장하면, seed에 실제로 있는 사실을 모두 보존할 수 있습니다.

또한 서로 어긋날 수 있는 두 개의 변경 가능한 원본(`like_count` counter + like row)을 관리하지 않아도 됩니다.

## 수용한 비용

`likeCount`에는 requester가 만든 좋아요에 대한 집계가 필요합니다. 이 과제의 데이터 크기에서는 mutable counter 비정규화보다 정확성과 명확성이 더 가치 있습니다.

# ADR-006 — Pagination: Cursor/keyset pagination with deterministic ordering

**상태:** `DECIDED`

## 결정

post와 comment 모두 cursor 기반 pagination을 씁니다.

기준 순서:

```text
ORDER BY created_at DESC, id DESC
```

cursor는 현재 page의 마지막 `(created_at, id)` 쌍을 나타냅니다. API는 필수 `items`와 `total` field를 유지하고 `nextCursor`를 추가합니다.

구현된 wire 계약:

```text
GET /api/posts?limit=20&cursor=<opaque>
GET /api/posts/{postId}/comments?limit=20&cursor=<opaque>

default limit: 20
valid limit: 1..50
omitted cursor: first page
invalid limit or cursor: HTTP 400
```

opaque cursor는 `<exact Instant text>|<id>`를 padding 없는 URL-safe Base64로 encode한 값입니다. timestamp를 epoch millisecond로 줄이지 않습니다. decoder는 canonical encoding과 유효한 양수 ID만 받습니다. repository는 `LIMIT + 1`을 쓰고, 요청한 limit까지만 반환하며, `OFFSET`은 쓰지 않습니다.

post 목록에는 이후 선택 parameter `sort`(`latest`/`likes`)와 `q`가 추가되었습니다. `likes` 정렬은 `(like_count, created_at, id)` keyset과 별도 `PostLikeCursorCodec`을 씁니다. parameter가 없으면 위 계약 그대로입니다("Post Discovery 반영" 참고).

개념적 응답 예시:

```json
{
  "items": [],
  "total": 39,
  "nextCursor": "opaque-value"
}
```

## 근거

- Assignment evidence: post와 comment는 최신순이며, 한 번에 전부가 아니라 page 단위로 로드해야 합니다.
- PostgreSQL은 `LIMIT`을 row를 고유한 순서로 제한하는 `ORDER BY`와 함께 써야 하며, 그렇지 않으면 page 부분집합을 예측할 수 없다고 설명합니다.
- PostgreSQL은 큰 `OFFSET`으로 건너뛴 row도 계산해야 한다고 설명합니다.
  - https://www.postgresql.org/docs/current/queries-limit.html

## 선택 이유

infinite scroll과 동시 생성에는 page 번호보다 위치 기반 cursor가 더 잘 맞습니다. tie-breaker로 `id`를 더하면 여러 row의 timestamp가 같아도 순서가 결정적입니다.

## Offset pagination을 쓰지 않은 이유

작은 seed에서는 순수 성능만 보면 offset pagination도 괜찮고 설명하기도 더 쉽습니다. 하지만 사용자가 scroll하는 동안 더 새로운 row가 들어오면 뒤쪽 offset이 밀려 중복·누락 가능성이 커지므로 선택하지 않았습니다.

## 수용한 비용

backend는 cursor를 encode/decode해야 하고, client는 임의의 page 번호로 바로 이동할 수 없습니다. product에 page 번호 UI가 없으므로 여기서는 문제가 되지 않습니다.

# ADR-007 — Frontend Server State: TanStack Query; local UI state stays local

**상태:** `DECIDED` — 구현 완료. provider와 query key 기반은 P3에서(P3 Frontend 기반 반영 참고), feature query/mutation hook은 P4–P6에서 구현했습니다.

## 결정

remote/server state에는 TanStack Query를 씁니다.

- 댓글 page,

## 수용한 비용

frontend dependency가 하나 늘고, query key와 invalidation을 의도적으로 설계해야 합니다. 직접 만들어야 할 비동기 상태 처리가 줄어드는 만큼 감수할 만한 비용입니다.

# ADR-010 — Infinite Scroll Trigger: `IntersectionObserver`

**상태:** `DECIDED` — 구현 완료. P0 당시에는 pagination과 server state가 미결이라 `PROVISIONAL`이었습니다.

## 결정

`IntersectionObserver`로 관찰하는 sentinel element로 다음 TanStack Query page를 요청합니다.

callback은 `hasNextPage`와 `isFetchingNextPage`로 보호합니다.

## 구현

- `frontend/lib/hooks/useInfiniteScrollTrigger.ts`는 기본 `rootMargin` `0px 0px 200px 0px`으로 sentinel을 관찰합니다. scroll 위치를 polling하지 않습니다. *(이후: post 목록은 500px를 넘기고 댓글 이어 읽기는 기본값을 유지합니다. List Prefetch Distance Decision 참고.)*
- 첫 교차에서 연결을 끊고 `onIntersect`를 한 번 호출하므로, 활성화 주기마다 요청은 하나입니다. `enabled`가 다시 true가 되면 새 observer를 만듭니다. 새 observer는 현재 교차 상태를 보고하므로, page가 로드된 뒤에도 sentinel이 보이면 scroll 없이 이어집니다.
- 호출하는 쪽은 요청 상태로 `enabled`를 보호합니다.
  - `PostListScreen`: `data !== undefined && hasNextPage && !isFetchingNextPage && !isFetchNextPageError`.
  - `CommentSection`: 위와 같고 `expanded`가 추가되어, "더보기" 전에는 아무것도 로드하지 않습니다.
- 다음 page가 실패하면 명시적 retry 전까지 trigger가 비활성 상태로 남아 loop하지 않습니다.

## 근거

- MDN은 `IntersectionObserver`가 대상이 viewport/조상 요소와 교차하는 시점을 비동기로 관찰하며, main thread에서 가시성을 계속 polling하지 않아도 된다고 설명합니다.
  - https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API

## 선택 이유

UI 요구는 "모든 scroll 위치에 반응"이 아니라 "사용자가 끝에 닿으면 다음 page를 로드"입니다. sentinel 교차는 그 조건에 대한 직접적인 browser primitive입니다.

## 수용한 비용

observer lifecycle을 올바르게 다뤄야 하지만, 직접 scroll 위치를 계산하는 것보다 단순하고 실수가 적습니다.

# ADR-012 — Backend Validation, Ownership, Transactions, and Error Handling

**상태:** `DECIDED`

## 결정

### Validation

backend request DTO는 validation dependency 없이 작은 명시적 validator를 씁니다.

- title: non-null, nonblank, `codePointCount` 기준 최대 20 Unicode code point
- post content: non-null, nonblank
- comment content: non-null, nonblank, 최대 길이는 추가하지 않음

blank 확인은 validation에만 쓰며, 허용된 값은 자동 trim 없이 저장합니다.

frontend validation은 UX를 위해 같은 규칙을 따르지만 최종 판단은 backend validation입니다.

### Ownership

requester는 결정적으로 판별합니다.

```text
x-user-id header > x-user-id cookie > apr_tester
```

과제는 header와 cookie를 모두 허용하지만 충돌 시 우선순위는 정하지 않으므로, 이 우선순위는 구현 결정입니다.

ownership 확인은 UI 표시에만 두지 않고 service/application layer에 둡니다.

### Transactions

mutation method의 transaction 경계는 service layer의 `@Transactional`에 둡니다. 6개 mutation method가 모두 여기에 해당합니다. row lock은 method마다 필요한 대상에만 겁니다.

| Mutation | 잠그는 row (`SELECT … FOR UPDATE`) |
| --- | --- |
| post 생성 | 없음 — 잠글 기존 row가 없음 |
| post 수정 / 삭제 | 읽을 수 있는 대상 post. 잠근 뒤 ownership 확인 |
| 좋아요 toggle | 읽을 수 있는 대상 post. 같은 post의 toggle을 직렬화하고, requester 중복은 `(post_id, user_id)` primary key가 막음 |
| 댓글 생성 | 읽을 수 있는 parent post |
| 댓글 삭제 | 읽을 수 있는 대상 댓글과 읽을 수 있는 parent post(`FOR UPDATE OF p, c`). 잠근 뒤 ownership 확인 |

request body validation은 lock을 잡기 전에 실행합니다. 대상이 없거나 soft delete되었으면 lock 단계에서 `404`가 됩니다.

### Errors

일관된 JSON error에 `@RestControllerAdvice`를 씁니다.

구현된 status 의미:

```text
400 validation / malformed input
403 authenticated-by-assignment requester does not own resource
404 missing or soft-deleted resource
201 successful creation
200 successful read/update/toggle
204 successful delete
```

과제는 동작이 올바르다면 status code 선택을 명시적으로 허용합니다.

## 근거

- Repository evidence: `MutationValidator`는 dependency 없이 null/blank와 Unicode code point validation을 수행하고, `ApiExceptionHandler`는 읽을 수 없는 JSON을 공통 error body로 바꿉니다. lock 대상은 `PostMutationService`, `CommentMutationService`, `PostRepository.findReadableMutationTargetForUpdate`, `CommentRepository.findReadableMutationTargetForUpdate`에 있습니다.
- Spring Framework는 선언적 `@Transactional` 지원을 설명합니다.
  - https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/declarative/annotations.html
- Spring MVC는 `@RestControllerAdvice`를 response body를 render하는 controller 전역 exception 처리로 설명합니다.
  - https://docs.spring.io/spring-framework/reference/6.2/web/webmvc/mvc-controller/ann-advice.html

## 수용한 비용

명시적 DTO/error mapping code가 조금 늘지만, validation·권한·HTTP 의미를 repository code 밖에 두고 frontend가 보안 경계가 되지 않게 합니다.

# ADR-013 — Seed Initialization: transactional, idempotent, source-preserving

**상태:** `DECIDED` — 구현 완료. P0 당시에는 migration 방식과 startup hook이 아직 없어 `OPEN`이었습니다.

## 결정

runtime `APP_SEED_PATH`를 과제 seed의 유일한 원본으로 씁니다.

최종 흐름(`backend/.../seed/SeedInitializer.java`, Flyway 이후 실행되는 `ApplicationRunner`이며 `run()`에 `@Transactional`이 붙어 있음):

```text
Flyway schema ready
    ↓
SeedInitializer.run() — one transaction:
  seed_history has "assignment-v1"?
    yes → register readiness after commit, stop
    no  → read seed.json
          insert posts with explicit IDs (deletedPostIds → is_deleted = TRUE)
          insert comments with explicit IDs (deletedCommentIds → is_deleted = TRUE)
          align post/comment identity sequences
          record seed_history marker "assignment-v1"
          register readiness after commit
    ↓
commit → SeedReadiness opens /health
```

초기 제안에서 바뀐 점은 두 가지입니다.

- sequence 정렬을 transaction 안, marker 기록 전으로 옮겼습니다.
- readiness gate를 추가했습니다. 아래 "해결"을 참고하세요.

첫 기동 뒤 user가 수정한 내용을 덮어쓸 수 있으므로, 재시작할 때마다 seed 값을 다시 적용하지 않습니다.

## 근거

- Assignment evidence: application 기동 뒤 데이터를 조회할 수 있어야 하고, 반복 기동이 seed 데이터를 중복시키면 안 됩니다.
- 제공 README: `seed/`는 `APP_SEED_PATH`를 통해 `/seed`에 read-only로 mount되고, PostgreSQL 데이터는 named volume에 유지됩니다.
- Spring Boot 3.5는 database 초기화 순서와 방식을 설명합니다.
  - https://docs.spring.io/spring-boot/3.5/how-to/data-initialization.html

## `COUNT(*) > 0`만 보지 않고 seed marker를 쓰는 이유

table이 비어 있지 않다고 해서 과제 seed가 완전히 성공적으로 import되었다는 뜻은 아닙니다. import transaction이 성공한 뒤에만 쓰는 전용 marker가 이 작업에 명시적인 의미를 줍니다.

## 원래 질문과 해결

*원래 질문 (P0):* 필수 `/health` 동작을 깨지 않으면서, application이 ready로 간주되기 전에 seed가 끝났음을 보장하는 lifecycle hook은 무엇인가?

**관찰한 문제:** `ApplicationRunner`만 쓰면 runner의 seed transaction이 commit되기 전에 Tomcat과 DB가 먼저 올라옵니다. starter `/health`는 DB 연결만 확인했으므로, 빈 상태 기동에서 `GET /api/posts`가 아직 `total` 0을 보고하는데도 `/health`는 200을 반환했습니다. 그러면 Compose가 backend를 healthy로 표시하고 seed되지 않은 database를 상대로 frontend를 시작할 수 있었습니다.

**해결:**

- `SeedReadiness.markReadyAfterCommit()`은 `afterCommit()`에서 ready flag를 켜는 `TransactionSynchronization`을 등록합니다. 새로 import하는 경로와 marker가 이미 있는 재시작 경로 모두에서 호출합니다.
- `HealthController`는 flag가 켜지기 전까지 503 `{"status":"starting","db":"up"}`을 반환합니다. 그 뒤에는 starter 계약대로 DB에 연결되면 200 `{"status":"ok","db":"up"}`을 반환합니다.
- 따라서 Compose의 `/health` healthcheck는 seed 데이터가 commit되어 조회 가능해진 뒤에만 backend를 healthy로 표시합니다.
- import가 실패하면 transaction이 rollback되고, marker는 기록되지 않으며, readiness는 열리지 않고, 다음 기동에서 import 전체를 다시 시도합니다.

**수용한 비용:** 첫 빈 상태 기동은 seed import가 끝날 때까지 healthy를 보고하지 않습니다(제공 seed 기준 약 0.9 s). readiness는 process별 in-memory flag입니다.

근거: `docs/VERIFICATION.md` "P8-A First-Boot Readiness Investigation"과 V-001/V-003.

# 2. Backend 구조

**상태:** `DECIDED` — `backend/src/main/java/com/apr/community/` 아래 실제 반영된 package 구성입니다.

구조는 얕고 feature 중심으로 유지하며, 구체적인 두 번째 구현이 없는 interface나 추상화는 두지 않습니다.

```text
com/apr/community/
├── CommunityApplication, CorsConfig        # starter
├── HealthController                        # starter path; readiness-gated (ADR-013)
├── common/
│   ├── error/        ApiErrorResponse, ApiException, ApiExceptionHandler
│   ├── pagination/   CursorCodec, CursorPosition, PageRequest, PageRequestParser, PageResponse
│   ├── requester/    RequesterResolver
│   └── validation/   MutationValidator
├── post/
│   ├── PostController                      # /api/posts/**, incl. nested comment list/create
│   ├── PostReadService                     # reads: list (latest/likes/search), detail, comments
│   ├── PostMutationService                 # create/update/delete, like toggle; ownership + transactions
│   ├── PostListRequest, PostListRequestParser, PostSort
│   ├── PostLikeCursor, PostLikeCursorCodec
│   └── PostMutationRequest, PostResponse, LikeToggleResponse
├── comment/
│   ├── CommentController                   # DELETE /api/comments/{commentId}
│   ├── CommentMutationService              # comment create/delete; ownership + transactions
│   └── CommentCreateRequest, CommentResponse
├── persistence/
│   ├── PostRepository, CommentRepository, PostLikeRepository
│   └── IdentitySequenceRepository, SeedHistoryRepository
└── seed/
    ├── SeedInitializer (ApplicationRunner), SeedReadiness
    └── SeedData, SeedDataReader
```

Schema: `backend/src/main/resources/db/migration/V1__create_community_schema.sql`.

Layer 책임:

```text
Controller  HTTP translation only (request parsing, requester resolution, status codes)
Service     validation, ownership, transactions, domain rules
Repository  SQL and row mapping (JdbcClient), no HTTP semantics
Common      cross-cutting rules: requester, validation, cursor/paging, JSON errors
```

**P0 이전 제안에서 바뀐 점.** 제안은 `PostService`와 `CommentService` 하나씩, `like/` package, `dto/` folder, `SeedLoader`/`SeedService`를 그렸습니다. 최종 code는 다음과 같이 다릅니다.

- post read와 mutation은 별도 service입니다. read는 pagination·정렬·검색을, mutation은 locking과 ownership을 맡기 때문입니다.
- 좋아요 toggle은 `PostMutationService`에 있습니다. 다른 post mutation처럼 post row를 잠그기 때문입니다.
- 모든 SQL repository는 `persistence/`에 모여 있습니다.
- request/response record는 controller 옆에 두며 `dto/` directory는 없습니다.
- seed는 `SeedInitializer`와 `SeedReadiness`가 맡습니다.

repository interface는 도입하지 않았습니다. 실제 test나 구현 경계가 생길 때만 interface를 추가합니다.

# 3. Frontend 구조

**상태:** `DECIDED` — `frontend/` 아래 실제 반영된 구성입니다.

```text
frontend/
├── app/                              # thin Server Component routes
│   ├── layout.tsx, providers.tsx     # QueryClientProvider + default retry policy (client boundary)
│   ├── page.tsx                      # /            → PostListScreen (first page via lib/api/server.ts)
│   ├── posts/new/page.tsx            # /posts/new   → CreatePostScreen (PostFormScreen.tsx)
│   ├── posts/[postId]/page.tsx       # detail       → PostDetailScreen
│   ├── posts/[postId]/edit/page.tsx  # edit         → EditPostScreen (PostFormScreen.tsx)
│   └── dev-user/                     # immutable starter code
├── features/                         # one folder per user flow
│   ├── post-list/    PostListScreen, PostListItem, PostListToolbar, usePostList, postListConfig
│   ├── post-detail/  PostDetailScreen, PostActionMenu, CommentSection, CommentComposer,
│   │                 ConfirmDialog, usePostDetail, useComments, useCommentMutations, useDeletePost
│   └── post-form/    PostForm, PostFormScreen, usePostFormMutations
└── lib/                              # shared across features: API, query cache, hooks, utilities
    ├── api/          client.ts (request), community.ts (endpoints), server.ts (SSR first page), types.ts
    ├── query/        keys.ts, postListCache.ts, retryPolicy.ts
    ├── hooks/        useInfiniteScrollTrigger, useSingleFlight
    ├── time/         relativeTime.ts, shortDate.ts
    ├── validation/   post.ts
    └── avatar.ts, flash.ts, formOrigin.ts, postId.ts, postListView.ts, requester.ts, routes.ts
```

`postListConfig.ts`는 `POST_LIST_PAGE_SIZE`와 `POST_LIST_PREFETCH_ROOT_MARGIN`을 담습니다. `"use client"` module에서 export한 값은 Server Component에서 쓸 수 없으므로, `app/page.tsx`와 client 목록이 같은 page size를 공유하도록 분리한 file입니다.

원칙:

- route file은 화면을 조합합니다.
- feature code가 product 동작을 맡습니다.
- 하나의 공용 API client가 base URL, JSON 처리, `credentials: "include"`를 맡습니다.
- TanStack Query가 remote state를 맡습니다.
- component local state가 일시적인 표시 상태를 맡습니다.

**P0 이전 제안에서 바뀐 점.** 제안은 feature를 entity별(`posts/`, `comments/`, `likes/`)로 묶고 공용 `components/` folder를 계획했습니다. 최종 code는 각 화면이 자신의 query, mutation, 상태를 가지므로 feature를 화면 흐름별(`post-list`, `post-detail`, `post-form`)로 묶습니다. 공유할 만큼 널리 쓰이는 visual primitive가 없어 `components/` folder는 만들지 않았습니다. style은 같은 위치의 `.module.css` file입니다.

# 4. P1/P3 이전 미결 사항 — 해결

P1/P3 전에는 문서만으로 다음을 확정할 수 없었습니다. 모든 항목은 이후 repository 근거로 해결했습니다.

| 결정 | 미결이었던 이유 | 해결 |
|---|---|---|
| 정확한 column 길이/type | seed 형태를 아직 점검하지 않음 | `V1` schema(ADR-004): `title VARCHAR(20)`, `TEXT` content/author, `TIMESTAMPTZ`, identity `BIGINT` ID |
| 정확한 seed startup hook | starter lifecycle/healthcheck와 맞춰야 함 | `ApplicationRunner` + `SeedReadiness` after-commit gate(ADR-013) |
| 정확한 Flyway dependency | Gradle file과 dependency management에 달려 있음 | `org.flywaydb:flyway-database-postgresql`, version은 Spring Boot BOM에서(ADR-002) |
| 최종 styling 선택 | 이미 설치된 starter system과 충돌하면 안 됨 | 설치된 것이 없었음; `globals.css` token + CSS Modules(ADR-009) |
| 정확한 frontend component tree | component 분해는 P4–P6의 일 | 위 "Frontend 구조" |
| 자동화된 DB integration test 방식 | test/build 환경에 맞아야 함 | Testcontainers `postgres:16-alpine`로 해결. 커밋된 6 suites / 31 tests가 실제 Spring context, Flyway, seed loader, repository로 실행되며, 동시성 test는 실제 transaction과 row lock을 씁니다. backend CI job은 전체 18 suites / 91 tests를 실행합니다. |

날짜가 붙은 phase section은 당시의 불확실성을 기록으로 남깁니다. 현재 architecture 기록은 위 표와 최종 ADR 상태입니다.
